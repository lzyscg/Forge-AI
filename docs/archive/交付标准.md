# Forge AI MVP 交付标准

> 本文件是 Forge AI MVP 的**终点线**。开发 Agent 完成返修清单中的具体缺陷后，必须逐项对照本标准进行自查，确认所有条款全部满足，才能声明 MVP 完成。
>
> **核心原则：任何一项标为"硬指标"的验收条款没有通过，整个 MVP 都不算完成，不得进入下一阶段。**

---

## 如何使用本文件

1. 开发 Agent 逐项执行下面的验收条款。
2. 每执行完一项，在该项末尾标注：
   - `PASS`（通过，附带证据）
   - `FAIL`（未通过，附带阻塞原因）
   - `N/A`（明确不在 MVP 范围内）
3. 全部条款为 `PASS` 或 `N/A` 后，把整份填好的文件连同证据一起提交给用户。
4. **不得在任何条款上写"基本完成""大体满足""测试覆盖率较高"——每项只有"满足/不满足"两种状态。**

## 第一章：架构与纪律铁律（全为硬指标）

### 铁律 1：不把任何业务写死进平台

**验收内容**
平台代码中不存在对业务角色名、场景名称、产物类型的硬编码分支。新增场景不需要修改任何 TypeScript 源代码。

**通过标准**
- [ ] 在 `packages/` 和 `apps/` 的所有 `.ts` 文件中搜索以下字符串，结果数量为 0：
  - `"supervisor"`、`"generator"`、`"reviewer"`、`"lyrics"`、`"songwriting"`、`"copywriting"`、`"文案"`、`"歌词"`、`"山歌"`
  - （允许出现在 `scenarios/` 目录下的 YAML/JSON/Markdown 文件中，因为这些是配置数据）
- [ ] `scenarios/copywriting/` 目录存在且包含独立的 `scenario.yaml` + 提示词 + Fake Pi 脚本。
- [ ] `packages/application/src/case-service.ts`（或 Case 创建入口）在创建 Case 时只读取传入的 `scenario_key`，没有对特定 key 做特殊处理。
- [ ] `packages/application/src/tool-executor.ts` 中不存在 `if (agentKey === 'xxx')` 这类分支。

**验证方式**
```bash
# 运行以下 grep，输出应为空
grep -r -i "supervisor\|generator\|reviewer\|lyrics\|songwriting\|copywriting\|文案\|歌词\|山歌" packages/ apps/ --include="*.ts" --include="*.tsx"
```

**失败情形**
- grep 结果非空（硬编码业务名称）
- 第二场景虽然目录存在，但 Fake Pi 仍返回歌词脚本的内容
- 运行第二场景需要修改 `apps/worker/src/main.ts` 或其他平台源代码

---

### 铁律 2：模型不碰工程数据

**验收内容**
Agent（模型）的输出里不应包含 case_id、session_id、version、时间戳、路由边、数据库字段。系统在处理工具调用时补齐这些字段。

**通过标准**
- [ ] 5+1 工具的定义中，Agent 可见的参数不包含任何 ID 字段：
  - `publish_artifact`：参数为 `artifact_type`、`content`、`summary`（无 `artifact_id`、`version`）
  - `submit_evaluation`：参数为 `verdict`、`issues`、`summary`（无 `case_id`、`evaluation_message_id`）
  - `route_message`：参数为 `target_agent`、`instruction`、`scope`、`reason`（无 `message_id`、`route_id`）
  - `approve_delivery`：参数为 `artifact_type`（或可选不传）（无 `artifact_version_id`）
  - `read`（受限，仅 skills 目录白名单）：参数为 `file_path`（无工程 ID）
- [ ] 提示词模板（`scenarios/*/prompts/*.md`）中没有要求模型返回 JSON、ID、版本号、时间戳的指令。
- [ ] 真实 Pi 运行日志中，模型的最终输出文本（不含系统包装）里没有出现 `case_`、`session_`、`msg_`、`artifact_` 等系统 ID 前缀。

**验证方式**
```bash
# 检查工具契约
cat packages/contracts/src/tools.ts | grep -E "artifact_id|version:|case_id|session_id|message_id|route_id"
# 期望：结果为空（类型定义本身不包含这些字段，是系统补齐的）

# 检查提示词
grep -r "id\|version\|case_id\|session_id" scenarios/*/prompts/
# 期望：结果为空（提示词不要求模型输出工程数据）
```

**失败情形**
- 工具定义里要求模型传 `artifact_version_id`
- 提示词里写"请返回 JSON，包含 case_id 和 version"
- 模型输出里包含系统生成的 ID

### 铁律 3：交付是系统的决定，不是 Agent 的声明

**验收内容**
Agent 调用 `approve_delivery` 不等于交付成功。系统必须独立核对 5 项条件，全部通过才把产物版本置为 `delivered`、Case 置为 `approved`。

**通过标准**
- [ ] `packages/domain/src/delivery-gate.ts`（或等效文件）包含 5 项独立检查，且代码注释明确对应以下 5 项：
  1. 申请交付的产物版本存在且状态有效（不是 `invalidated` / `superseded`）
  2. 该产物版本已经过审核通过（`approved` 状态，且不继承自旧版本）
  3. 所有 `blocking` 级 Issue 状态为 `verified`
  4. 没有运行中的返修指令（`issued` / `in_progress` / `submitted`）
  5. 没有未完成的 Turn（非 `completed`）
- [ ] `claimed_fixed` 状态的 Issue **绝对不能**通过门禁。
- [ ] 单元测试覆盖：有一项测试模拟 `claimed_fixed` 的 blocking Issue 存在，断言门禁 `passed = false`。
- [ ] 单元测试覆盖：有一项测试模拟旧版本已 `approved`、新版本未审核，断言门禁 `passed = false`。

**验证方式**
```bash
npm run test -- packages/domain/src/delivery-gate.test.ts
# 断言：全部通过，且测试列表包含上述两个边界条件
```

**失败情形**
- 门禁检查少于 5 项
- `claimed_fixed` 能通过门禁
- 新版本自动继承旧版本的 `approved` 状态

---

### 铁律 4：一切追加，绝不覆盖

**验收内容**
产物新版本追加，不覆盖旧版本。Issue 状态变化以事件追加记录。崩溃恢复不允许覆盖已成功持久化的结果。

**通过标准**
- [ ] `artifact_versions` 表：同一 `artifact_id` 下有多个版本记录，`version` 字段递增，旧版本不会被 `UPDATE` 覆盖。
- [ ] `issue_events` 表：同一 `issue_id` 下有多个事件记录（`created` → `repairing` → `verified`），不是单条记录反复 `UPDATE`。
- [ ] 崩溃恢复测试（12.2）中，重启后已完成 Turn 的 `output_message_id`、`produced_artifact_version_ids`、`context_snapshot_id` 与重启前完全一致（内容哈希不变）。
- [ ] 数据库迁移脚本里没有 `ON UPDATE CASCADE` 或 `REPLACE` 语义覆盖旧版本。

**验证方式**
```bash
# 跑完一个 Fake Pi 全链路后查询 SQLite
sqlite3 <db_path> "SELECT artifact_id, version, status FROM artifact_versions ORDER BY artifact_id, version;"
# 期望：同一 artifact_id 有多行，version 递增，旧版本状态仍为 superseded/approved（不是被删除或覆盖）

sqlite3 <db_path> "SELECT issue_id, event_type FROM issue_events ORDER BY issue_id, created_at;"
# 期望：同一 issue_id 有多行，展示完整生命周期
```

**失败情形**
- 旧版本被 UPDATE 成新内容
- Issue 状态变化只更新单行记录，没有追加事件
- 崩溃恢复后已完成产物版本的 content_hash 发生变化

---

### 铁律 5：架构依赖只能单向

**验收内容**
代码分层：`contracts → domain → application → adapters → apps`。`domain` 不依赖数据库/Pi/Web 框架。`adapters` 不含业务角色名分支。`apps/web` 不直接调用 Pi。

**通过标准**
- [ ] `packages/domain/` 下没有任何文件 import `better-sqlite3`、`@earendil-works/pi-coding-agent`、`@earendil-works/pi-ai`、`next`、或其他非 `node:` 内置模块和 `@forge-ai/contracts` 的内容。
- [ ] `packages/application/` 只通过 `RepositoryPort`、`PiPort`、`ClockPort`、`IdGeneratorPort` 等接口调用外部依赖，没有直接 import SQLite 或 Pi 的实现类。
- [ ] `apps/web/` 不 import `@earendil-works/pi-coding-agent` 或 `@earendil-works/pi-ai`。
- [ ] `apps/worker/` 是唯一启动 Pi Session 的入口。

**验证方式**
```bash
# 架构依赖检查（如果没有现成的 architecture:check 脚本，手动执行以下 grep）
# domain 层不能出现外部依赖
grep -r "better-sqlite3\|pi-coding-agent\|pi-ai\|next" packages/domain/ --include="*.ts"
# 期望：空

# web 不能出现 Pi
grep -r "pi-coding-agent\|pi-ai" apps/web/ --include="*.ts" --include="*.tsx"
# 期望：空
```

**失败情形**
- `domain` 层直接调用了数据库或 Pi SDK
- `web` 层直接创建了 Pi Session
- `adapters` 层存在业务角色分支

### 铁律 6：不泄密

**验收内容**
API Key、Token、Authorization Header、模型隐藏思维链，绝不进入日志、数据库业务表、或返回给前端。

**通过标准**
- [ ] `apps/web/` 的 API 响应中不包含 `Authorization`、`api_key`、`token` 字段。
- [ ] SQLite 数据库的 `messages`、`context_snapshots`、`control_events` 表中不包含 `sk-` 或 `DEEPSEEK_API_KEY` 等敏感字符串。
- [ ] 运行日志（`npm run dev` 输出）不包含完整的 API Key，即使出错也脱敏显示。
- [ ] 前端回放页显示的模型输出只包含最终文本和工具调用，不展示 thinking 原文。

**验证方式**
```bash
# 搜索数据库敏感信息
sqlite3 <db_path> ".dump" | grep -i "api_key\|sk-\|DEEPSEEK\|authorization"
# 期望：空

# 搜索日志文件
grep -r "sk-\|DEEPSEEK_API_KEY\|Authorization" logs/ 2>/dev/null
# 期望：空
```

**失败情形**
- 数据库里存了 API Key
- 前端能看到模型的 thinking 原文
- 日志里打印了完整的 Authorization Header

## 第二章：核心机制验收（全为硬指标）

### 验收 2.1：Fake Pi 全链路闭环

**验收内容**
使用 Fake Pi 完成一次歌词场景的完整生产闭环：初稿 → 审核打回 → 定点返修 → 复审通过 → 申请交付 → 系统门禁通过 → Case `approved`。

**通过标准**
- [ ] `npm run dev` 或 `npm run test` 中包含一个 Fake Pi 全链路测试，运行后 Case 最终状态为 `approved`。
- [ ] 数据库记录：
  - `turns` 表 ≥ 7 条记录（总控分配、生成 v1、审核 v1、总控返修、生成 v2、审核 v2、总控交付）
  - `artifact_versions` 表有 v1（`superseded`）和 v2（`delivered`）
  - `evaluation_issues` 表有一条 blocking issue，状态从 `open` → `repairing` → `claimed_fixed` → `verified`
  - `delivery_gate_results` 表有一条记录，5 项检查全部 `passed`
- [ ] 生成 Agent（`generator`）的 Session 为 `persistent`，审核 Agent 的 Session 为 `cold_per_version`（数据库 `agent_sessions` 表中 policy 字段）。

**验证方式**
```bash
npm run test -- <fake-pi-integration-test-path>
# 运行后查询 SQLite，确认上述记录存在
```

**失败情形**
- Case 最终状态不是 `approved`
- 缺少 `delivery_gate_results` 记录
- Issue 状态跳跃（比如直接从 `open` 跳到 `verified`，没有 `claimed_fixed`）
- 生成 Agent 用了多个 Session（`persistent` 策略未生效）

---

### 验收 2.2：真实 Pi 全链路验证（最高风险硬指标）

**验收内容**
接入真实 Pi（`@earendil-works/pi-coding-agent` SDK + 底层模型配置），完成一次完整歌词生产闭环。这是整个 MVP 风险最高的假设——验证"模型在最小结构化约束下能否稳定协作"。

**通过标准**
- [ ] 运行命令：`PI_MODE=real npm run dev`（或等效命令），使用真实模型调用。
- [ ] Case 最终状态为 `approved`（不是手动强制设置，是系统门禁自然通过）。
- [ ] 每个 Turn 的 `context_snapshot` 记录存在，且 `rendered_context` 字段包含真实发给模型的完整上下文（可脱敏，但保留结构）。
- [ ] `tool_actions` 表中有真实模型触发的工具调用记录，参数正确。
- [ ] 产物 v2 与 v1 的 diff 仅包含返修指令要求修改的范围（行级），没有整段重写。
- [ ] 保留运行日志或 SQLite 数据库 dump 作为证据。

**特别注意**
- 如果真实模型在运行中表现不稳定（比如不服从 `editable/frozen` 范围、审核证据不可靠），**这不等于验收失败**，但必须：
  1. 如实记录不稳定的表现和具体 Turn
  2. 调整提示词或工具定义后重新验证
  3. 在交付报告中写明"经过 N 轮调整，当前配置下模型可稳定协作"
- **严禁用 Fake Pi 的结果冒充真实 Pi 验收。**

**验证方式**
```bash
# 运行真实 Pi 全链路
PI_MODE=real npm run dev
# 完成后查询数据库确认状态
sqlite3 <db_path> "SELECT status FROM cases WHERE case_id = '<the_case_id>';"
# 期望：approved
```

**失败情形**
- 没有真实 Pi 运行证据
- Case 状态为 `approved` 但缺少 `delivery_gate_results`（跳过了门禁）
- v2 与 v1 的 diff 超出返修范围（说明模型不服从约束，且系统没有拦截）
- 运行日志/SQLite dump 缺失

### 验收 2.3：崩溃恢复（硬指标）

**验收内容**
流程跑到一半时 kill 进程，重启后从最后一个完成的 Turn 续跑，已完成产物版本未被重新生成。

**通过标准**
- [ ] 可重复执行的自动化测试（或手动脚本）证明：
  1. 在 Turn N 完成后、Turn N+1 开始前 kill worker 进程
  2. 重启 worker，Case 状态先变为 `waiting_recovery`，再恢复为 `running`
  3. 从 Turn N+1 开始续跑（不是从 Turn 1 重跑）
  4. 最终 Case 状态为 `approved`
- [ ] 重启前后，Turn 1 到 Turn N 的 `output_message_id`、`produced_artifact_version_ids` 完全不变（内容哈希一致）。
- [ ] `persistent` Session 的生成 Agent 在续跑后，上下文包含之前 Turn 的历史（从 `context_snapshot` 可验证）。

**验证方式**
```bash
# 运行崩溃恢复测试
npm run test -- <crash-recovery-test-path>
# 或手动执行 kill + 重启脚本
```

**失败情形**
- 重启后从 Turn 1 开始重跑
- 已完成产物版本被重新生成（content_hash 改变）
- `persistent` Session 续跑后丢失历史上下文（`context_snapshot` 不包含之前内容）
- Case 没有先经过 `waiting_recovery` 状态

### 验收 2.4：配置化 / 通用性（硬指标）

**验收内容**
不修改平台任何源代码，只写一份新的 YAML + Fake Pi 脚本 + 提示词，就能跑通第二个业务场景。

**通过标准**
- [ ] `scenarios/copywriting/` 目录包含完整的 `scenario.yaml`、`prompts/*.md`、`fake-pi-script.json`。
- [ ] 运行 `npm run dev` 时传入 `SCENARIO_PATH=scenarios/copywriting/scenario.yaml`（或等效方式），Case 能正常创建并运行。
- [ ] 数据库中该 Case 的 `scenario_snapshot` 与歌词场景的 `scenario_snapshot` 不同。
- [ ] 数据库中该 Case 的 Agent 为 `writer` / `qc`（而不是 `supervisor` / `generator` / `reviewer`）。
- [ ] 数据库中该 Case 的产物类型为文案场景定义的类型（不是 `lyrics`）。
- [ ] Fake Pi 返回的脚本内容与歌词场景不同。

**验证方式**
```bash
# 运行第二场景
SCENARIO_PATH=scenarios/copywriting/scenario.yaml npm run dev
# 查询数据库确认
sqlite3 <db_path> "SELECT scenario_snapshot FROM cases;"
sqlite3 <db_path> "SELECT agent_key FROM agent_sessions;"
sqlite3 <db_path> "SELECT artifact_type FROM artifacts;"
```

**失败情形**
- 需要修改 `apps/worker/src/main.ts` 或其他平台代码才能跑第二场景
- Fake Pi 仍返回歌词脚本的内容
- 数据库里产物类型仍是 `lyrics`

### 验收 2.5：职责边界（硬指标）

**验收内容**
证明"中间层接管工程格式"和"系统独立掌握真相"这两根支柱成立。

**通过标准**
- [ ] 业务 Agent（生成/审核）的输出里没有 case_id / session_id / version / 时间戳 / 路由元数据（真实 Pi 运行日志可验证）。
- [ ] 格式问题不会导致整轮业务内容白白重生成（没有"因为 JSON 格式不对就重跑"的记录）。
- [ ] 交付由系统门禁决定，Agent 的 `approve` 单独不足以交付（门禁未全绿时，即使 Agent 调了 `approve_delivery`，Case 也不变 `approved`）。
- [ ] 越界返修被系统拦截，该版本状态为 `rejected`，不能进入复审。
- [ ] `claimed_fixed` 状态不能作为门禁通过的依据。
- [ ] 新增 Agent、修改提示词、调整模型和增减允许路由不需要修改后端代码（已通过 2.4 验证）。

**验证方式**
- 审查真实 Pi 运行日志中的模型输出文本
- 审查 `delivery_gate_results` 表的记录
- 审查 `artifact_versions` 表中状态为 `rejected` 的记录及其 diff

**失败情形**
- 模型输出包含系统 ID
- 门禁未全绿但 Case 变成了 `approved`
- 越界修改未被拦截，进入了复审

---

### 验收 2.6：只读回放 Web 页面

**验收内容**
一个基础的只读回放页面，能在浏览器中查看 Case 的运行过程、产物版本、Issue 状态和门禁结果。

**通过标准**
- [ ] 页面按场景配置显示 Agent 泳道（至少显示 Agent 名称和消息卡片）。
- [ ] 每条消息显示：类型、内容摘要、发送者、接收者、时间、轮次。
- [ ] 能查看产物各版本及行级 Diff（至少显示改了哪些行、哪些行被冻结）。
- [ ] 能查看每个 Issue 的证据、当前状态、修复版本、验证记录。
- [ ] 能查看交付门禁的逐项结果（哪项通过、哪项不通过、原因）。
- [ ] 使用轮询刷新（不做 SSE）。
- [ ] 页面从 SQLite 只读连接读取数据，不直接调用 Pi。

**非目标（这些可以不做，做了也不算加分）**
- 跨泳道连线动画
- SSE 实时推送
- 样式精修、响应式设计、移动端适配
- 产物依赖图可视化

**验证方式**
```bash
# 启动 web 服务
cd apps/web && npm run dev
# 浏览器打开 http://localhost:<port>/cases/<case_id>
# 手动验证上述 6 项功能
```

**失败情形**
- 页面无法加载 Case 数据
- 缺少产物版本 Diff 展示
- 缺少 Issue 状态展示
- 缺少门禁逐项结果

## 第三章：工程细节验收

### 验收 3.1：事务原子性

**通过标准**
- [ ] `TurnExecutor.executeTurn` 的核心逻辑（状态翻转 + 副作用写入）包在一个 SQLite 事务内。
- [ ] 如果 `executeTurn` 中途抛出异常，已写入的 `tool_actions`、`artifact_versions`、`messages` 等记录不会残留在数据库中（事务已回滚）。

**验证方式**
- 新增故障注入测试：Mock Pi adapter 在 callback 执行完第一个工具后抛出异常
- 断言：数据库中没有 `pending` 状态的 `tool_action`，没有该工具产生的 `artifact_version`

**失败情形**
- 真实 Pi 路径（callback 分支）的工具写入不在事务内
- 异常后数据库残留部分写入记录

## 第五章：不可接受的"完成"声明

以下情况出现时，即使其他条款全部通过，也**不得声明 MVP 完成**：

1. **没有真实 Pi 运行的任何证据**（日志、SQLite dump、截图、录屏至少一项）。
2. **真实 Pi 运行中使用了 `pi-ai` 包而不是 `pi-coding-agent` 包作为 Agent 运行时**——这等于仍然没有验证 Pi 的真实 Agent 层。
3. **崩溃恢复测试是从 Fake Pi 的内存态模拟的，而不是真实 kill worker 进程 + 重启**——内存态的"恢复"不等于进程级恢复。
4. **测试中有大量 `skipped` 或 `todo` 但没有明确说明原因**——跳过困难测试不等于通过。
5. **交付报告中存在"后续优化""待完善"等模糊措辞掩盖验收失败**——每项只有 pass/fail，没有"基本完成"。

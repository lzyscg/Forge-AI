# Forge AI MVP 返修清单

> 审查者：Claude（基于 PLAN.md 与 Forge_AI_MVP_需求文档.md）
> 审查对象：Forge-AI-main 完整代码库
> 审查方式：只读代码审查 + Pi 官方文档独立核实（`pi.dev/docs/latest`、`github.com/earendil-works/pi`）
> 审查结论：**未达到 MVP 验收标准**，存在 3 项 P0 阻断缺陷、2 项 P1 严重缺陷、2 项 P2 证据缺失。以下按优先级排序，必须逐项修复并提供可运行证据。

## P0 阻断缺陷（不修复则整个 MVP 验收不通过）

### P0-1：真实 Pi Adapter 接入的是错误的包——没有真正对接 Pi 的 Agent Runtime

**问题简述**
`@forge-ai/adapters` 依赖的是 `@earendil-works/pi-ai`（`package.json:34`、`pi-adapter.ts:20-21`），而 Pi 官方仓库 `earendil-works/pi` 的 README 明确说明：
- `@earendil-works/pi-ai` = "Unified multi-provider LLM API（OpenAI、Anthropic、Google 的薄封装）"
- `@earendil-works/pi-coding-agent` = "Agent runtime with tool calling and state management"

真正的 Agent Session、SessionManager、工具循环、事件订阅、持久化/恢复能力，**全部在 `pi-coding-agent` 包里**。当前 `pi-adapter.ts` 自己手写了一个 `MAX_TOOL_ITERATIONS` 循环 + 自己维护 Context 数组 + 自己实现 `persistent`/`cold_per_version`——这**本质上还是绕开了 Pi 的 Agent 层**，只是从"直连 DeepSeek"改成了"用 Pi 的模型库自己搭 Agent 循环"，形式合规、实质偏离。

**违反了什么**
- PLAN.md "Guardrail: no silent architecture substitution"（不能静默替换已锁定的架构决策）
- 原始需求文档 §4.2 "Pi First"："不自行重新实现模型 Provider、上下文窗口和 Agent 循环"
- PLAN.md Risks："崩溃恢复与 Session 策略抽象依赖 Pi 真实能力，尚未验证"——当前完全没有验证，只是用手写代码绕过了它

**具体位置**
- `Forge-AI-main/package.json:34`：`"@earendil-works/pi-ai": "^0.82.0"`
- `Forge-AI-main/packages/adapters/src/pi-adapter.ts:15-23`：import 来源为 `pi-ai`
- `Forge-AI-main/packages/adapters/src/pi-adapter.ts:33-284`：整个 `RealPiAdapter` 基于 `pi-ai` 的 `createModels` / `deepseekProvider` / `Context` 对象实现，没有使用 `createAgentSession` / `SessionManager` / `AgentSession`

**必须改成什么样**
1. 将依赖改为 `@earendil-works/pi-coding-agent`（如果存在版本兼容问题，先向用户汇报，不得自行决定退回 `pi-ai`）。
2. 参考 Pi 官方 SDK 文档（`pi.dev/docs/latest/sdk`）重新实现 `RealPiAdapter`：
   - `createSession()` → 调用 `createAgentSession({ sessionManager: SessionManager.inMemory(), ... })` 或 `SessionManager.create(cwd)`
   - `executeTurn()` → 通过 `session.prompt()` 发送消息，通过 `session.subscribe()` 接收事件（`turn_start`, `turn_end`, `tool_execution_start/end`, `message_update`）
   - 工具注册 → 通过 `customTools: [defineTool(...)]` 传入 `createAgentSession` 选项，或在 session 创建后 `session.agent.state.tools = [...]`
   - 底层模型 → 由 Pi 的 `ModelRuntime` 管理，Forge 只指定 model id / thinking level，不直接调用 `deepseekProvider()`
3. `persistent` / `cold_per_version` 的语义必须映射到 Pi 原生 Session 机制：
   - `persistent`：同一个 Forge `session_id` 对应同一个 Pi Session 文件，跨 Turn 复用
   - `cold_per_version`：每次新建一个 Pi Session（`SessionManager.create()` 或 `runtime.newSession()`）
4. **不得**在 adapter 里自己实现工具调用循环。Pi 的 Agent 层已经内置了 "prompt → model → tool call → execute → model sees result → continue" 的循环，Forge 只需要订阅事件并在 `tool_execution_start/end` 时执行自己的 `toolExecutor` 回调。

**怎么验证修好了**
- 新增一个**零 Token 消耗**的探测测试（`packages/adapters/src/pi-adapter.probe.test.ts`）：
  1. 安装 `@earendil-works/pi-coding-agent`（不需要真实 API Key，用 in-memory session）
  2. 调用 `RealPiAdapter.createSession('supervisor', 'persistent')`，断言返回的 `session_ref` 对应一个真实可订阅的 Pi AgentSession
  3. 注册一个假工具（`noop_tool`），调用 `executeTurn`，断言 Pi 的事件流里出现 `tool_execution_start` 和 `tool_execution_end`
  4. 断言 `executeTurn` 返回的 `tool_calls` 里有稳定的 `provider_tool_call_id`（同一 Turn 内不变）
- 运行 `npm run test`，该探测测试必须通过。

### P0-2：`persistent` Session 崩溃恢复后丢失历史——resumeSession() 创建的是空 Context

**问题简述**
`RealPiAdapter.resumeSession()`（`pi-adapter.ts:93-104`）在 session 不在内存时，直接创建一个新的空 Context：
```typescript
sessionState.context = { messages: [], tools: [] }
```
而 `persistent` 策略的含义是"跨 Turn 复用同一 Session，保留之前的创作上下文"。这意味着如果 worker 进程崩溃重启，恢复出来的"persistent Session"是**没有任何历史消息的空壳**，生成 Agent 会丢失之前的创作上下文，等于从头开始写。

这是 MVP 验收 12.2（崩溃恢复）和 12.1（定点返修需继承原 Session）同时失败的根源。

**违反了什么**
- MVP 需求文档 §9.2 第 7 步："系统按返修作用域恢复原生产 Session"
- PLAN.md Approach 第 9 步："断言已完成产物版本未被重新生成"——但产物没被重新生成不代表**生成过程**没被重新做（因为上下文丢了，模型可能输出不同内容）

**具体位置**
- `Forge-AI-main/packages/adapters/src/pi-adapter.ts:93-104`：`resumeSession()` 方法

**必须改成什么样**
1. 如果使用 `pi-coding-agent` 的 `SessionManager.create(cwd)`，Pi 本身会把 Session 历史持久化到 `~/.pi/agent/sessions/` 的 JSONL 文件，`resumeSession` 应通过 `SessionManager.open(sessionFilePath)` 或 `SessionManager.continueRecent(cwd)` 恢复真实历史。
2. 如果因为 MVP 限制必须使用 `SessionManager.inMemory()`，则 Forge 自己的数据库必须在 `agent_sessions` 表里保存足够信息（或另开一张 `session_context_history` 表），`resumeSession` 时从数据库重建 Context，**绝不能创建空 Context**。
3. 无论哪种方案，`resumeSession` 的返回值必须能支撑后续 `executeTurn` 时模型看到之前完整的对话历史（system prompt + 所有 user/assistant/tool 消息）。

**怎么验证修好了**
- 崩溃恢复测试（`apps/worker` 或集成测试）必须新增断言：
  1. 跑完 Turn 1（生成 Agent 产出 v1）→ kill 进程
  2. 重启 worker，恢复同一 Case 和 Session
  3. 继续跑 Turn 2（返修指令）
  4. **断言**：Turn 2 的 `context_snapshot.rendered_context` 包含 Turn 1 的输出内容（即历史被继承了）
  5. **断言**：v2 的 diff 只包含返修指令要求的修改，不包含"因为丢失上下文导致的整段重写"

### P0-3：真实 Pi 路径的工具执行缺少事务原子性

**问题简述**
`turn-executor.ts` 有两个分支执行工具：
- **分支 A（真实 Pi callback）**：`pi.executeTurn(session, messages, tools, toolExecutor)`，其中 `toolExecutor` 回调里直接执行 `insertToolAction` + `toolExecutor.execute` + `updateToolAction`（`122-169 行`），**没有任何事务包裹**。
- **分支 B（Fake Pi fallback）**：`runInTransaction(() => { ... })`（`183-234 行`），有事务。

这意味着：如果真实 Pi 调用过程中，工具已经执行、产物已经写入，但进程在 `updateToolAction` 或后续 `insertMessage` 之前崩溃，恢复时会看到一个" Turn 状态 = running、但工具动作不完整、产物已存在"的混乱状态——并且因为幂等键只查 `tool_actions`，重试时可能再次执行同一工具，产生重复产物。

**违反了什么**
- PLAN.md Approach 第 6 步："每个 Turn 的状态翻转与全部副作用必须在同一个数据库事务内提交"
- PLAN.md Key Decision："Turn 状态翻转与副作用同事务"是 Round 1 评审后强制加入的，现在只在 Fake Pi 路径落实

**具体位置**
- `Forge-AI-main/packages/application/src/turn-executor.ts:56-283`：整个 `executeTurn` 方法
- 特别：`122-169` 行（callback 分支无事务）和 `183-234` 行（fallback 分支有事务）

**必须改成什么样**
1. 整个 `executeTurn` 的核心逻辑（从 `updateTurn(status='running')` 开始，到最终 `updateTurn(status='completed')` 或 `updateTurn(status='failed')` 结束）必须包在一个 SQLite 事务内。
2. `RepositoryPort` 接口已提供 `beginTransaction()` / `commitTransaction()` / `rollbackTransaction()` / `runInTransaction()`，必须在 `TurnExecutor.executeTurn` 的最外层使用。
3. 如果 `pi.executeTurn` 的 callback 模式不支持"先收集所有工具动作、最后统一提交"，则改为：callback 里只记录工具动作到内存数组，等 Pi 返回后再统一写入数据库（此时已在外层事务中）。

**怎么验证修好了**
- 新增故障注入测试（`packages/application/src/turn-executor.fault.test.ts`）：
  1. Mock Pi adapter：在 callback 执行完第一个工具、但 `executeTurn` 还没返回时抛出异常
  2. 断言：数据库里没有该 Turn 的 `completed` 状态
  3. 断言：数据库里没有该工具产生的 `artifact_version`
  4. 断言：数据库里没有该工具的 `tool_action` 记录（或如果已插入则是 `pending` 且整个事务已回滚）

## P1 严重缺陷（影响验收可信度，但不阻断编译）

### P1-1：Fake Pi 的幂等键机制是假的——回归测试测的不是宣称的东西

**问题简述**
`fake-pi.ts` 有两处导致幂等测试无效：
1. `executeTurn` 永远取第一个 script（`81 行：this.scripts.keys().next().value`），与 scenario 无关；
2. 工具调用 ID 按 `turnIndex + i` 动态生成（`106 行：fake_tc_${turnIndex}_${i}`），同一 Turn 重试时 ID 会变。

`turn-executor` 里的幂等检查 `getToolActionByProviderId(turnId, providerToolCallId)` 因此永远匹配不上，但测试之所以还能"过"，是因为 `publish_artifact` 里有一层兜底的内容哈希去重（`tool-executor.ts:109-117`）。**测试名字说在测"幂等键"，实际测的是"内容哈希去重"**。

这是旧项目 `HANDOFF.md` 里同一个翻车模式的重演（Idempotency-Key 字段存在但逻辑未生效）。

**具体位置**
- `Forge-AI-main/packages/adapters/src/fake-pi.ts:81`：script 选择逻辑
- `Forge-AI-main/packages/adapters/src/fake-pi.ts:106`：`provider_tool_call_id` 生成逻辑
- `Forge-AI-main/packages/application/src/turn-executor.ts:124-129`：幂等检查逻辑（基于 provider_tool_call_id）
- `Forge-AI-main/packages/application/src/tool-executor.ts:109-117`：兜底的内容哈希去重

**必须改成什么样**
1. `FakePiAdapter` 必须支持按 `scenarioId` 路由到对应 script（而不是永远取第一个）。
2. 同一 Turn 的 `provider_tool_call_id` 必须**稳定**——可以用 `turnId + toolName + toolIndex` 的组合，确保重试时不变。
3. **单独写一个回归测试**，明确验证"幂等键"路径：
   - 直接调用 `ToolExecutor.execute('publish_artifact', ...)` 两次，传入相同的 `turnId` 和相同的 `provider_tool_call_id`
   - 断言第二次返回的 `artifact_version_id` 与第一次相同（不是新生成的）
   - 断言数据库里该 `turnId + provider_tool_call_id` 组合只有一条 `tool_action` 记录

**怎么验证修好了**
- 运行 `npm run test`，新增的这个幂等键回归测试必须通过，且测试注释里明确说明"验证 provider_tool_call_id 去重，不依赖内容哈希兜底"。

### P1-2：12.3 "第二场景零代码验证"在逻辑上跑不出真实结果

**问题简述**
因为 Fake Pi 永远返回第一个 script（`fake-pi.ts:81`），即使加载了 `copywriting/scenario.yaml`，Fake Pi 执行时仍然返回 `songwriting` 的脚本。这意味着：
- 数据库里可能存的是 copywriting 的配置，但 Fake Pi 产生的工具调用、产物内容全是歌词
- "零代码改动跑通"这个验收从逻辑上无法区分"平台真的通用"和"平台只是硬编码了第一个场景"

**具体位置**
- `Forge-AI-main/packages/adapters/src/fake-pi.ts:75-84`：`executeTurn` 的 script 选择逻辑

**必须改成什么样**
1. `FakePiAdapter.executeTurn` 必须接收 `scenarioId` 参数（或从 session / context 中推断），按 scenario 选择对应 script。
2. 或者：在 `registerScript` 时明确绑定 `scenarioId`，`executeTurn` 时根据当前 Case 的 scenario 取对应 script。
3. `copywriting` 场景的 Fake Pi 脚本必须产生与歌词场景**不同的** Agent key、不同的工具调用序列、不同的产物类型。

**怎么验证修好了**
- 第二场景验收测试必须断言：
  1. Case 创建时使用的 scenario_key = `copywriting`
  2. 数据库里该 Case 的 artifact_type = `copywriting_output`（或该场景定义的类型），不是 `lyrics`
  3. 参与的 Agent key 包含 `writer` / `qc`（而不是 `supervisor` / `generator` / `reviewer`）
  4. 页面回放页能正确显示 copywriting 的 Agent 泳道

## P2 证据缺失（不是代码缺陷，是"声称完成但没有可运行证据"）

### P2-1：12.1 真实 Pi 全链路验证——没有任何可运行证据

**问题描述**
PLAN.md 和 MVP 需求文档都把"真实 Pi 全链路验证"列为**最高风险硬指标**，但代码库里没有任何证据表明它被执行过：
- 没有真实模型调用日志（无论成功还是失败）
- 没有真实运行后生成的 SQLite 数据库 dump
- 没有测试报告或截图
- `DEEPSEEK_API_KEY` / `PI_MODEL_ID` 环境变量是否配置过无从确认

**必须改成什么样**
返修完成后，必须提供以下至少一项可运行证据：
1. 一个 SQLite 数据库文件，包含真实 Pi 运行产生的完整 Case / Turn / Message / Artifact / Issue 记录（可脱敏，但保留结构）；或
2. 一份运行日志（`npm run dev` 输出），显示真实 Pi 从 Case 创建到 `approved` 的完整过程，包含每个 Turn 的耗时、Token 数、工具调用序列；或
3. 一个录屏或截图，显示 worker 进程真实调用 Pi、Case 最终状态为 `approved`。

**特别注意**：如果真实 Pi 在运行中表现不稳定（模型不服从 editable/frozen 范围、审核证据不可靠等），**这不等于验收失败**——验收的目的是"验证机制是否成立"，如果模型行为不稳定，应如实记录为"真实 Pi 行为需要调整提示词/工具定义"，并调整方案后重新验证。隐瞒不稳定比暴露不稳定更严重。

## 返修完成后必须重新跑的全套验证清单

按这个顺序执行，每步都必须有证据：

1. **编译检查**：`npm run check` → 0 错误
2. **单元测试**：`npm run test` → 全部通过（含新增的真实 Pi 探测测试、幂等键回归测试、故障注入测试）
3. **Fake Pi 全链路**：`PI_MODE=fake npm run dev` + 歌词场景 → Case 状态 `approved`
4. **Fake Pi 第二场景**：`PI_MODE=fake npm run dev` + copywriting 场景 → Case 状态 `approved`，断言数据库产物类型不是歌词
5. **真实 Pi 能力探测**：`npm run test -- packages/adapters/src/pi-adapter.probe.test.ts` → 通过（不消耗 Token，验证 pi-coding-agent SDK 可加载、Session 可创建、工具可注册）
6. **真实 Pi 全链路**：`PI_MODE=real npm run dev` + 歌词场景 → Case 状态 `approved`，保留完整日志/SQLite dump
7. **崩溃恢复**：在流程跑到一半时 kill worker 进程 → 重启 → 断言 Case 经过 `waiting_recovery` → 续跑 → `approved` → 断言已完成产物版本 content_hash 不变
8. **交付门禁逐项检查**：从 SQLite 查询 `delivery_gate_results` 表，确认 5 项检查都有记录，且 `passed = true`

## 返修纪律提醒（直接复制自 AGENTS.md）

- **完成声明必须有可运行证据**：每一项上面的"怎么验证修好了"都是硬性要求，不能只写"已修复"三个字。
- **真实 Pi 全链路验证是 MVP 硬指标，不能只用 Fake Pi 顶替**。
- **在真实 Pi 和崩溃恢复验证通过前，不打磨 UI**。
- **如果某个已锁定的架构决策（如必须使用 `pi-coding-agent`）在实践中难以落地，必须先停下来向用户报告偏离原因和替代方案，获得明确确认后才能采用替代实现**——不得自行简化或绕过。

# 交付报告：返修生命周期一致性 + Case 恢复修复

> 本报告记录 Forge AI 返修生命周期 bug 的修复交付。任务书：`Forge返修指令关闭与Case恢复修复任务书.md`。修复提交：`75428f6`。

---

## 1. 概述

真实运行（`zhihu-story-outline` 场景，多轮返修）暴露返修生命周期不一致问题：Issue 已被复审标 `verified`，但承载它的 Revision Instruction 仍 `submitted`，导致交付门禁 `no_active_revision` 拦截，Case 静默停在 `repairing`。

本次按任务书 5.1-5.6 修复 4 个根因 + 1 个恢复消息缺口，新增 7 组回归测试，经 harness（dev + review agent）执行 + 主 agent 复核。**核心修复完成，验收通过。**

---

## 2. 问题复现

| 项 | 值 |
|---|---|
| 日期 | 2026-07-26 |
| Scenario | `zhihu-story-outline` |
| 模型 | `deepseek-v4-flash` |
| Case | `case_42376dcd693f43a1`（11 Turn，5 个大纲版本） |

**最终表象**：最终大纲版本 `approved`、所有 blocking Issue `verified`、所有 Turn `completed`，但 Forge 门禁失败：

```
no_active_revision = false
存在 2 个未完成的返修指令：ri_33f61daddd59401c(submitted) ri_e6d8dc24fb9441ab(submitted)
```

Case 停在 `status=repairing, completed_at=null`。最后一轮 Agent 无工具调用，CaseRunner 直接结束循环返回非终态。

**数据不一致**：`issue_*` 已 `verified`，但其所属 `ri_*` 仍 `submitted`。另有两条新建 `issued` 指令的 `issue_ids` 字段实际写入的是 Revision Instruction ID（`["ri_33f61...", "ri_e6d8..."]`），说明 `route_message` 接受任意字符串作 `issue_ids`。

## 3. 根因（已核实，对照代码）

| # | 根因 | 代码位置 | 核实 |
|---|---|---|---|
| 3.1 | `submit_evaluation(approve)` 只关**第一条** submitted 指令，却把**全部** claimed_fixed Issue 转 verified | `tool-executor.ts:297` `filter(claimed_fixed)` 全取 + `:305` `find(submitted)` 取首条 | ✅ 直接根因 |
| 3.2 | `publish_artifact` 隐式取**最后一条**活跃指令，无目标 Agent/版本校验 | `tool-executor.ts:138` `activeInstructions[len-1]` | ✅ |
| 3.3 | `route_message` 不校验 `issue_ids`（存在性/同 Case/状态），错误 ID 直接入库 | `tool-executor.ts:399-406` | ✅ |
| 3.4 | 非终态 Case 无工具调用时静默 `break` 退出，不查 Case 状态 | `case-runner.ts:482-484` | ✅ |
| 3.5 | `buildResumeContextMessage` 信息不足（只"活跃返修指令 N 条"，无 ID/状态/issue/目标） | `case-runner.ts` | ✅ |

**为何之前未发现**：songwriting/copywriting 的 Fake Pi 全链路只有一轮返修（v1->v2），单条 submitted 指令，3.1/3.2 的多指令悬挂不触发。真实大纲场景多轮返修（5 版本）才暴露。是真实的覆盖盲区。

## 4. 修复（任务书 5.1-5.6 + 额外）

| 项 | 修复内容 | 文件 |
|---|---|---|
| 5.1 | `submit_evaluation(approve)` 重写：收集 Case 全部 submitted 指令，先 `findUnresolvableSubmittedInstructions` 检测部分状态（有 Issue 仍 repairing/open/reopened -> `PARTIAL_REVISION_INCOMPLETE` 结构化错误、不改状态），再 `applyEvaluationVerify`（重构为接受多指令）同事务批量关指令 + `claimed_fixed->verified` + 版本 `->approved` | tool-executor.ts, state-transitions.ts |
| 5.2 | `publish_artifact` 按 `(target_agent=当前发布方, target_artifact_version_id=父版本)` 确定性绑定唯一活跃指令；0 条 `NO_ACTIVE_INSTRUCTION`、>1 `AMBIGUOUS_ACTIVE_INSTRUCTION`，均不发布。`route_message` 新建时同 `(case,target_agent)` 已有 `issued\|in_progress` 指令则合并 issue_ids/anchors（**单活跃约束**，submitted 视为不同轮次可共存） | tool-executor.ts |
| 5.3 | `route_message` 写入前逐个校验 `issue_ids`（存在 + `issue.case_id===当前 Case` + `status in open\|reopened`）；任一非法返回 `success=false` + `INVALID_ISSUE_REFERENCE` + `invalid_issue_ids`，不写指令、不改 Issue 状态。覆盖不存在 ID / RI ID / 跨 Case / 已 verified 四类 | tool-executor.ts, tools.ts |
| 5.4 | 非终态无工具调用：查 Case 状态；`approved`/`waiting_human` 正常结束；`repairing`/`waiting_review`/`running` 第一次追加 `buildCorrectionMessage`（列活跃指令+Issue+允许工具）重试，连续第二次转 `failed` + `agent_no_action_in_nonterminal_state` 控制事件。不再静默 break | case-runner.ts |
| 5.5 | `buildResumeContextMessage` 改富上下文（Case 状态 / 最新版本+hash / 全部未关闭 Issue 的 ID+severity+status+anchor / 全部活跃指令的 ID+status+target_agent+target_version+issue_ids / 下一步允许动作）+ 新增 `decideResumeAgent` 程序化恢复决策（under_review->审核、issued\|in_progress->指令 target_agent、全关闭未交付->start_agent 申请交付、无法归类->回退） | case-runner.ts |
| 5.6 | `approve_delivery` 门禁唯一失败项 `no_active_revision` 时，对关联 Issue 已全 `verified` 的陈旧 `submitted` 指令执行一致性修复（`->verified`，记 `consistency_repair` 事件）并重评估门禁；仍失败按指令状态确定性路由（submitted->审核 Agent、issued/in_progress->target_agent），无法归类报 `INTERNAL_STATE_INCONSISTENT`。case-runner 据结果 `route_to` 路由而非把门禁文本丢给 start agent | tool-executor.ts, case-runner.ts |
| 额外 | `recovery.ts` 事件 ID 原用 `Date.now()`，同毫秒重复 `recoverCase` 触发 `control_events` UNIQUE 冲突（4.5 幂等漏洞）-> 改进程级计数器保证唯一 | recovery.ts |

**未走任务书第 6 节捷径**：未删 `no_active_revision` 门禁项；`submitted` 仍在 active 集合（`isRevisionInstructionActive` 不变）；未批量无条件关指令（`submit_evaluation` 只关可解析指令、`approve_delivery` 只关陈旧指令）；`repairing` Case 不允许正常返回 success（5.4 转 failed）；未新建 Case 绕过。

**实现范围**：未改 `revision-instruction-state.ts` 与 `sqlite-repository.ts`（任务书第 8 节列为"建议"）：状态机不变，仍用 JSON `issue_ids` 列，5.3 校验集中在 `route_message` 写入口（含 5.2 越界重试拷贝已校验过的 issue_ids），符合任务书"若继续使用 JSON 字段，必须确保所有写入口都经过同一校验"。

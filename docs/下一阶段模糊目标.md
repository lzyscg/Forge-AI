# Forge AI 下一阶段模糊目标

> 本文档用于记录下一阶段的方向性目标，而不是详细需求、技术方案或实施计划。
>
> 这些目标允许在后续讨论中持续拆分、修正和补充。现阶段只确定“要走向哪里”，暂不锁定“具体怎么做”。

## 总体方向

下一阶段要把 Forge AI 从当前偏工程验证性质的多 Agent Case 平台，逐步建设成一个可以由用户直接操作、观察和管理内容生产流程的产品。

这一阶段包含两个相互关联的目标：

1. 建设新的 Forge UI，让平台现有能力以清晰、统一、可操作的方式呈现出来。
2. 将当前位于 Forge 外部的多 Case 编排能力逐步纳入 Forge，使多个模板之间能够在平台内部完成产物流转、状态管理和恢复，并为这套能力提供对应的 UI。

这两个目标不是彼此孤立的项目。UI 应当随着平台能力逐步演进，编排能力也应当从用户如何理解和操作流程的角度进行设计。

## 模糊目标一：建设新的 Forge UI

新的 UI 不应只是现有页面的视觉美化，而应逐步成为 Forge 的主要操作界面。

它最终需要帮助用户理解和操作以下对象：

- 模板及模板具备的生产能力；
- 单个 Case 的运行状态、Agent 协作过程和当前进度；
- 产物及其版本、审核结果、Issue 和返修关系；
- 系统门禁为何通过或未通过；
- 预定义编排流程及其各阶段的运行情况；
- 需要人工处理、恢复或重新运行的异常状态。

当前阶段先追求信息结构清晰、关键状态可信、常用操作顺畅。具体视觉风格、页面数量、导航结构和交互细节留待后续逐步明确。

## 模糊目标二：将编排器能力纳入 Forge

当前 `story-pipeline` 已经证明了多个 Forge Case 可以按照固定顺序完成输入交接、产物传递、身份绑定、机械校验、恢复和下游失效传播。

下一阶段希望把这类能力从“Forge 外部的故事专用编排器”，逐步演进成“Forge 内部可复用的多模板编排能力”。

这套能力的大致方向包括：

- 一个流程可以引用多个已有模板；
- 上游正式产物可以按明确规则成为下游模板的输入；
- Forge 能记录流程、阶段、Case、产物和父子依赖关系；
- 流程中断后可以安全恢复，而不是从头重复生产；
- 上游发生变化时，可以识别并处理受影响的下游阶段；
- 每个阶段仍然保留自己的内容审核和系统交付门禁；
- 编排层负责工程流转，不替代各模板对内容质量的判断；
- 整个过程具有可查询、可解释、可验证的运行证据。

首版不建设自由拖拽、任意连线的流程设计器。首版只支持由系统预先定义好的流程，并在 UI 中完成流程选择、启动、观察和必要的操作。

预定义流程的具体表达方式、存储位置和运行模型，后续再单独设计。

## 两个目标之间的关系

UI 和编排能力计划按照逐步汇合的方式推进：

1. 先梳理 Forge 现有对象和操作，建立新的 UI 基础。
2. 明确 Forge 内部编排能力需要具备的最小通用概念。
3. 将现有外部编排器中已经验证有效的能力逐步迁入或抽象进 Forge。
4. 在 UI 中加入预定义流程的入口、流程进度、阶段详情、产物流转和异常状态。
5. 使用真实流程验证平台内编排、恢复、门禁和 UI 展示的一致性。

每一步都应形成可运行、可验证的纵向切片，避免先做出一套脱离真实运行状态的完整界面，也避免只完成后台能力而长期没有用户可用的操作入口。

## 暂定原则

后续细化和实现仍需遵守 Forge 已有的核心原则：

- 平台保持配置驱动，不把知乎故事等具体业务写死进通用代码；
- 模型负责内容，系统负责 ID、版本、状态、路由、血缘和门禁；
- 编排成功和阶段交付必须由系统证据决定；
- 产物、事件和历史记录继续采用追加式管理，不覆盖有效历史；
- 发现身份、输入、父版本或证据不一致时保持 fail closed；
- UI 展示的状态必须来源于真实持久化数据，不能创造另一套状态；
- 真实 Pi 链路、崩溃恢复和幂等验证仍然是完成标准的一部分；
- 在关键后台能力和恢复链路得到验证前，不以视觉完成度代替系统完成度。

## 暂不进入当前目标的内容

以下内容目前不作为首版范围：

- 自由拖拽节点和连线的可视化流程设计器；
- 面向任意复杂分支、循环和动态条件的通用工作流语言；
- 与 Forge 内容生产无关的通用自动化平台能力；
- 在编排协议尚未稳定前进行大量纯视觉打磨；
- 为了兼容旧数据而削弱身份、门禁、恢复或证据校验。

这些方向未来可以重新评估，但不应阻塞预定义流程在 Forge 内部落地。

## 阶段性成功信号

在不提前规定具体实现的前提下，下一阶段可以用以下信号判断方向是否成立：

- 用户可以通过新的 UI 看懂并操作一个 Forge Case；
- 用户可以在 Forge 中选择并启动一个预定义流程；
- 用户可以看到流程各阶段、对应 Case、输入输出和当前状态；
- 阶段之间的产物流转由 Forge 自动完成，不需要人工复制文件或拼接命令；
- 流程中断后能够从已有证据安全恢复；
- 上游失效能够被系统识别，并反映到下游状态和 UI；
- 最终结果仍然通过各阶段门禁和编排层证据校验；
- 至少一条真实故事生产链路能够在 Forge 内部完成并留下完整证据。

## 后续持续细化的主题

后续可以围绕以下主题逐个形成更具体的目标、设计和实施计划：

- 新 UI 的用户角色、导航和核心工作台；
- Case、模板、流程、流程运行和阶段之间的产品概念；
- 预定义流程的声明方式和版本管理；
- 阶段输入输出映射与产物类型契约；
- 编排运行状态、持久化边界和恢复语义；
- 现有 `story-pipeline` 能力的迁移、保留或重构边界；
- 流程级失效传播、替换和历史追溯；
- 人工介入、重试、停止和恢复的交互；
- 编排详情页与 Case 详情页之间的关系；
- 真实 Pi、崩溃恢复、并发和端到端验收方式；
- UI 视觉语言、组件体系和响应式范围。

每个主题在进入开发前，都可以从本文档的模糊目标出发，逐步形成独立的设计文档和实施计划。

# Forge UI 需求文档

> 状态：持续细化中  
> 当前版本：0.13
> 首次建立：2026-07-28  
> 默认第一用户：内容生产操作者

## 1. 文档定位

本文档是 Forge UI 产品化的长期需求入口。

当前先记录已经确认的产品方向、功能范围、交互需求、可视化需求和待讨论问题。后续每次确认的新需求、范围调整和产品决策，都继续更新到本文档中。

本文档暂不等同于最终设计稿或实施计划。尚未确认的内容应保留为候选需求或待细化项，不能因为被记录在本文档中就自动视为已经批准开发。

## 2. 背景

Forge 当前已经具备多 Agent Case 运行、产物版本管理、审核 Issue、受控返修、交付门禁、人工暂停和崩溃恢复等工程能力。

现有 Web 页面可以创建、运行和恢复 Case，并以泳道形式回放 Turn、路由、工具调用、产物版本、Issue 和门禁结果。但整体仍偏向工程验证和技术回放，尚未形成面向内容生产操作者的完整产品体验。

Forge UI 产品化的目标不是单纯美化现有页面，而是重新组织平台能力，让内容生产操作者能够直接理解和操作一次生产任务。

## 3. 产品定位

Forge UI 是内容生产操作者使用 Forge 的主要操作界面。

它应当优先帮助用户回答以下问题：

1. 我有哪些生产任务？
2. 某个任务现在进行到哪里？
3. 当前由哪个 Agent 或系统环节处理？
4. 已经生成了什么结果？
5. 当前是否存在审核问题或返修任务？
6. 为什么任务暂停、失败或不能交付？
7. 现在是否需要我进行操作？
8. 最终交付结果是什么，依据是否完整？

开发、调试和审计能力仍然保留，但不应占据默认界面的主要位置。

### 3.1 顶层核心对象：生产任务

Forge UI 面向用户的顶层核心对象统一称为“生产任务”。

- 当前由单个模板运行产生的 Case，是一种生产任务；
- 未来由预定义编排流程产生的流程运行，也是一种生产任务；
- 工作台、列表、搜索、筛选、待办和结果都围绕生产任务组织；
- `Case`、`Turn`、`Session` 等术语降为内部执行对象，只在生产详情或高级诊断中出现；
- 后续加入编排器时，不另起一套与生产任务割裂的顶层产品概念。

“生产任务”是用户概念，不要求当前代码立即把 Case 数据表重命名。产品概念与技术对象如何映射，在技术需求阶段单独设计。

## 4. 用户定位

### 4.1 默认第一用户

默认第一用户是内容生产操作者。

该用户需要创建任务、观察生产进度、查看结果、理解审核问题、处理人工介入和获取最终交付，但不应被要求理解数据库、执行租约、内部消息协议或其他平台实现细节。

### 4.2 次级用户

次级用户包括：

- 模板维护者；
- Forge 开发人员；
- 运行与故障排查人员；
- 需要审计生产证据的管理者。

次级用户所需的原始上下文、工具调用、哈希、内部 ID 和控制事件，应放入高级视图或诊断视图。

## 5. 产品目标

### 5.1 核心目标

- 让内容生产操作者能够从 UI 创建并运行 Forge 任务；
- 让用户快速判断任务状态、当前进度和下一步行动；
- 让产物、审核、Issue、返修和门禁形成连贯的产品体验；
- 让异常、暂停和恢复具有明确、可信的交互；
- 让 UI 展示的状态与 Forge 真实持久化状态保持一致；
- 为后续预定义编排流程 UI 预留一致的产品概念和界面扩展空间。

### 5.2 非目标

当前不以以下事项为目标：

- 自由拖拽和任意连线的流程设计器；
- 在普通用户界面中暴露全部工程字段；
- 允许用户手工修改 Case、Issue、版本或门禁状态；
- 用前端临时状态代替 Forge 的真实运行状态；
- 在后台能力尚未成立时制作不可运行的“演示型 UI”；
- 把知乎故事等具体业务写死进通用 UI。

## 6. 产品信息分层

Forge UI 的信息分为三层。

### 6.1 用户层

默认直接展示：

- 任务名称和用途；
- 当前状态和生产进度；
- 当前处理者；
- 当前产物；
- 待处理事项；
- 阻塞原因；
- 最终结果。

### 6.2 生产层

在任务详情的二级视图中按需展示：

- Agent 协作过程；
- Turn 和消息路由；
- 产物版本；
- 审核结果和 Issue；
- 返修指令和修改范围；
- 交付门禁；
- 恢复和人工介入记录。

### 6.3 诊断层

默认折叠，仅供高级用户查看：

- Case、Turn、Session、Message 等内部 ID；
- 原始工具参数和工具结果；
- 上下文快照；
- provider 错误；
- 控制事件；
- 内容哈希和模板身份；
- 数据库来源和执行租约信息。

API Key、runner token 和其他凭据在任何层级都不得展示。

## 8. 功能域需求

### UI-FR-001 工作台

工作台是用户进入 Forge 后的默认入口。

已经确认：首页首先服务于继续处理已有生产任务，而不是以模板选择或新建表单作为默认主体。

工作台的信息优先级为：

1. 需要人工处理的任务；
2. 异常或被阻塞的任务；
3. 正在运行的任务；
4. 最近更新和最近完成的任务。

“新建生产任务”需要作为工作台上的显著入口，但不能挤占当前待办和运行状态的主要注意力。

候选功能：

- 展示运行中、等待人工、异常、已完成任务数量；
- 展示需要用户立即处理的任务；
- 展示最近创建和最近更新的任务；
- 提供任务搜索和常用筛选；
- 从工作台快速进入创建任务或任务详情；
- 后续支持展示预定义编排流程运行。

主要交互：

- 按状态、模板、环境和时间筛选；
- 搜索任务名称或标识；
- 点击待办直接进入需要处理的位置；
- 快速创建新任务。

适合的可视化：

- 状态统计卡；
- 待办队列；
- 最近任务列表；
- 状态分布。

### UI-FR-002 模板中心

模板中心帮助用户理解 Forge 当前可以完成哪些生产任务。

候选功能：

- 查看模板名称、用途和说明；
- 查看模板需要的输入；
- 查看模板包含的 Agent 及其职责；
- 查看模板产出的正式产物类型；
- 查看模板版本和校验状态；
- 从模板直接创建任务。

主要交互：

- 搜索、筛选和选择模板；
- 查看模板详情；
- 根据模板发起任务；
- 高级用户查看模板原始配置和校验结果。

适合的可视化：

- 模板卡片；
- Agent 角色关系；
- 输入到产物的简单关系图。

### UI-FR-003 创建任务

创建任务应当由模板配置驱动，不为具体业务写死表单。

已经确认创建任务支持两种完成方式：

- 主操作“创建并运行”：保存任务并立即进入生产；
- 次操作“保存草稿”：保存当前输入，稍后继续补充或启动。

草稿需要作为工作台和任务列表中的明确状态展示，用户可以重新进入草稿继续填写。

任务输入遵循以下生命周期规则：

- 草稿阶段允许修改输入；
- 任务一旦启动，本次任务的原始输入立即冻结；
- 运行中和终态任务都不允许原地修改输入；
- 用户需要修改输入时，使用“基于此任务创建新任务”；
- 新任务复制原任务输入并允许用户修改；
- 原任务、原输入、产物和审核证据完整保留；
- 新旧任务之间需要保留可查询的来源关系。

候选功能：

- 选择模板；
- 根据 `input_fields` 动态生成输入表单；
- 填写任务名称；
- 选择允许的运行环境和模型模式；
- 显示必填项和输入错误；
- 在启动前展示任务摘要；
- 创建后自动进入任务详情。
- 基于已有任务复制输入并创建新任务。

主要交互：

- 分组填写字段；
- 长文本输入；
- 文件或素材输入能力后续单独确认；
- 保存草稿；
- 创建并启动；

具体自动保存、手动保存和离开页面提醒方式后续细化。

### UI-FR-004 任务管理

任务管理覆盖 Case 列表和 Case 生命周期操作。

第一版采用扁平的生产任务列表，不要求用户先创建项目或工作空间。

任务组织方式包括：

- 搜索；
- 状态、模板、环境和时间筛选；
- 排序；
- 标签。

项目或工作空间仅作为未来可选分组能力保留，不进入第一版必需范围。后续即使增加分组，生产任务仍保持为顶层核心业务对象，项目只负责组织任务。

任务归档和删除遵循以下规则：

- 所有状态的任务都支持归档和取消归档；
- 归档只影响默认列表中的可见性，不修改任务状态和生产证据；
- 草稿任务可以移入回收站；
- 任务一旦启动，普通用户不允许永久删除，只能归档；
- 已启动任务的输入、产物、Issue、返修、门禁和审计证据必须保留；
- 管理员级永久清理和数据保留策略留到技术与运维需求阶段讨论。

运行中任务的人工控制遵循以下规则：

- 同时提供“暂停”和“停止”；
- 暂停是在系统确认的安全边界停止继续执行，之后允许恢复；
- 暂停是运行中任务更常用、更安全的控制操作；
- 停止会把任务结束为终态，不能原地继续；
- 停止必须二次确认，并明确说明影响；
- 暂停和停止都不删除已经完成的 Turn、产物、Issue、门禁或审计证据；
- 安全暂停边界、当前 Turn 的处理和恢复语义在技术需求阶段确定。

任务异常后的可恢复性由系统根据执行证据判定，而不是交给用户盲目选择：

- 可安全恢复的任务进入等待恢复状态，并提供“从中断处恢复”；
- 不可安全恢复的任务进入失败终态，仅提供“基于此任务创建新任务”；
- UI 应解释系统的判定结果、异常发生位置以及已经保留的证据；
- 不提供强制重试、强制恢复或跳过证据校验的操作；
- 具体判定条件、幂等边界和恢复机制在技术需求阶段确定。

候选功能：

- 查看全部可访问任务；
- 按状态、模板、环境和时间筛选；
- 搜索任务；
- 查看任务更新时间、当前阶段和结果摘要；
- 启动尚未运行的任务；
- 暂停正在运行的任务；
- 恢复已暂停的任务；
- 停止允许停止的任务；
- 从系统判定的安全中断处恢复任务；
- 明确终态任务不可继续运行；
- 基于已有任务创建新任务；
- 后续确认归档、删除和批量操作是否需要。

主要交互：

- 搜索和组合筛选；
- 排序；
- 分页或增量加载；
- 状态相关操作菜单；
- 归档、取消归档和查看归档任务；
- 草稿移入回收站；
- 危险操作确认。

### UI-FR-005 任务概览

任务概览是生产任务详情的默认首屏。详情页首先回答“任务进行到哪里、现在需要做什么、当前结果是什么”，不直接把 Agent 执行过程作为主视图。

必须优先展示：

- 任务名称和模板；
- 当前 Case 状态；
- 当前处理者或等待对象；
- 阶段与步骤进度；
- 当前有效产物；
- 未解决 Issue 数量；
- 当前是否处于返修；
- 最新门禁状态；
- 是否需要人工操作；
- 最近一次重要事件。

任务概览应提供到当前产物、阻断 Issue、返修和门禁证据的快捷入口，但不在首屏展开完整执行细节。

Agent 泳道、Turn、消息路由、工具调用和原始运行证据统一进入二级“执行记录”视图。用户可以从概览中的状态、事件或异常定位到对应执行记录。

任务概览不应要求用户先阅读完整泳道或执行日志才能判断任务状态。

任务进度遵循以下产品规则：

- 以模板定义的阶段和步骤为基础，不在通用 UI 中写死业务阶段；
- 每个步骤展示已完成、进行中、等待或阻塞等离散状态；
- 明确标识当前阶段、当前步骤和可执行的下一步；
- 第一版不展示缺乏可靠依据的完成百分比或预计完成时间；
- 发生重复审核或返修时，单独展示当前轮次和历史轮次；
- 阶段、步骤与内部 Case 状态、Turn 的映射规则留到技术需求阶段确定。

适合的可视化：

- 任务状态条或阶段进度条；
- 当前处理节点；
- 结果、Issue、返修和门禁摘要卡；
- 阻塞横幅。

### UI-FR-006 Agent 协作过程

该功能位于任务详情的二级“执行记录”视图，用于解释一次生产任务内部发生了什么，不作为普通用户进入任务详情后的默认主视图。

候选功能：

- 展示模板中配置的 Agent；
- 展示每个 Agent 的名称、职责、模型和会话策略；
- 展示 Turn 顺序和状态；
- 展示 Agent 之间的消息路由；
- 展示每个 Turn 产生的产物或工具行为；
- 展示失败 Turn 和 provider 错误；
- 支持从 Turn 跳转到相关消息、产物或 Issue。

主要交互：

- 展开或折叠 Turn；
- 查看 Turn 输入和输出；
- 查看工具行为摘要；
- 高级模式查看原始工具参数和上下文。

适合的可视化：

- Agent 泳道；
- 时间线；
- 路由箭头；
- Turn 状态和耗时。

### UI-FR-007 产物与版本

产物是 Forge 产品体验中的核心对象。

候选功能：

- 展示当前正式产物；
- 展示所有历史版本；
- 区分 draft、under_review、approved、rejected、superseded、delivered 等状态；
- 展示版本父子关系；
- 展示版本摘要和创建来源；
- 选择任意两个版本比较；
- 复制或导出产物；
- 从版本跳转到相关审核、Issue、返修和门禁。

主要交互：

- 切换版本；
- 选择比较基准；
- 查看完整内容；
- 复制、下载或导出；
- 跳转到版本相关证据。

适合的可视化：

- 版本链；
- 版本状态；
- 行级或块级 Diff；
- 当前有效版本突出显示。

### UI-FR-008 审核与 Issue

审核与 Issue 用于说明产物存在什么问题，以及问题是否真正关闭。

候选功能：

- 展示 Issue 的严重程度、问题描述、锚点和证据；
- 展示 Issue 所属产物版本；
- 展示 `open → repairing → claimed_fixed → verified` 生命周期；
- 展示 Issue 事件历史；
- 区分阻断交付和非阻断问题；
- 从 Issue 定位到产物对应位置；
- 从 Issue 查看关联返修指令和修复版本；
- 支持按状态和严重程度筛选。

主要交互：

- 点击 Issue 跳转到产物锚点；
- 筛选未解决或 blocking Issue；
- 展开问题证据和事件；
- 查看修复前后版本。

适合的可视化：

- Issue 状态链；
- 严重程度标记；
- Issue 与版本的关联；
- 未解决问题分组。

### UI-FR-009 返修管理

返修管理用于解释“要求修改什么、允许修改什么、实际修改了什么”。

候选功能：

- 展示返修目标 Agent；
- 展示关联 Issue；
- 展示目标产物版本；
- 展示 editable 和 frozen 范围；
- 展示返修指令状态；
- 展示返修版本；
- 展示是否发生 scope violation；
- 展示越界后系统如何拒绝并继续处理。

主要交互：

- 从返修指令跳转到相关 Issue；
- 从返修范围跳转到对应产物位置；
- 比较返修前后版本；
- 展开返修事件历史。

适合的可视化：

- editable/frozen 行覆盖层；
- 修改行高亮；
- frozen 修改越界标红；
- Issue、指令和版本关联链。

### UI-FR-010 交付门禁

交付门禁必须明确表达“交付是系统决定，不是 Agent 声明”。

候选功能：

- 展示最新门禁结果；
- 展示历史门禁结果；
- 独立展示五项检查；
- 展示每项检查的解释；
- 失败项跳转到对应产物、Issue、返修或 Turn；
- 突出展示最终 delivered 版本；
- 不提供绕过门禁的普通 UI 操作。

五项检查：

1. 产物版本存在且有效；
2. 当前版本审核通过；
3. 所有 blocking Issue 已 verified；
4. 无运行中的返修；
5. 无未完成 Turn。

适合的可视化：

- 五项检查清单；
- pass/fail 总状态；
- 阻断来源；
- 历史门禁时间线。

### UI-FR-011 人工介入

人工介入覆盖 Case 进入 `waiting_human` 后的用户操作。

候选功能：

- 明确提示任务已安全暂停；
- 展示 Agent 请求人工介入的原因和问题；
- 提供回答输入；
- 提交后恢复 Case；
- 防止重复提交；
- 展示提交结果和恢复状态；
- 保留人工回答的审计记录。

主要交互：

- 输入回答；
- 提交确认；
- 恢复后的状态反馈；
- 对长答案、附件等输入形式后续继续确认。

### UI-FR-012 异常与恢复

异常与恢复应让用户知道发生了什么、系统保留了什么、现在可以做什么。

候选功能：

- 展示 Case failed、stopped、waiting_recovery 等状态；
- 展示用户主动暂停、恢复和停止事件；
- 展示最近错误和发生位置；
- 展示恢复事件；
- 展示哪些 Turn 和产物已经安全保留；
- 由系统判定当前任务是否可以安全恢复；
- 对可安全恢复的 Case 提供“从中断处恢复”；
- 对不可安全恢复的 Case 只提供“基于此任务创建新任务”；
- 对并发占用或执行租约冲突提供可理解的提示；
- 对不可恢复或身份不一致的情况保持 fail closed；
- 不提供伪造状态或跳过证据校验的操作。

适合的可视化：

- 异常横幅；
- 控制事件时间线；
- 恢复前后状态；
- 已保留与待重做范围。

### UI-FR-013 审计与诊断

审计与诊断面向高级用户，默认折叠。

候选功能：

- 查看完整 Turn；
- 查看消息；
- 查看工具调用参数和结果；
- 查看上下文快照；
- 查看 route edge 和 control event；
- 查看 provider 错误；
- 查看模板、输入和产物身份；
- 复制脱敏后的诊断信息。

诊断视图必须继续遵守不泄密要求。

### UI-FR-014 环境管理

Forge 当前区分 production、test 和 all。

候选功能：

- 明确展示当前环境；
- 切换 production、test 和 all；
- `all` 作为只读聚合视图；
- 在不同环境使用明显但不过度干扰的视觉标识；
- 在只读环境禁用写操作并解释原因；
- 危险操作前再次确认目标环境。

### UI-FR-015 Agent 模型配置

Forge UI 需要让用户看到每个 Agent 使用的模型，并允许在受控范围内修改。

已经确认的需求：

- 模板详情展示每个 Agent 配置的模型；
- Case 详情展示每个 Agent 在该次运行中实际使用的模型；
- UI 支持修改 Agent 的模型选择；
- 模板维护者可以修改 Agent 的默认模型，修改只影响之后创建的任务；
- 任务处于草稿阶段时，用户可以基于模板默认值覆盖本次任务的 Agent 模型；
- 任务启动时冻结每个 Agent 的实际运行模型；
- 运行中和终态任务不允许直接更换模型；
- 已启动任务需要更换模型时，基于原任务创建新任务；
- Case 恢复和续跑默认继续使用启动时冻结的原模型；
- 模板默认模型、任务草稿覆盖值和任务实际运行模型需要明确区分并可查询；
- 模板中声明的 `agent.model` 必须真正控制 Pi Agent Session 使用的模型，不能只作为展示字段；
- Forge 负责解析、传递并记录最终生效的模型；
- 模型提供商适配、模型调用和 Agent Runtime 继续复用 Pi 的能力；
- Provider 凭据不写入模板，也不在普通 UI 中展示；
- 不允许把 API Key 等凭据记录到 Case、日志或前端数据中。

需要在详细设计时确定：

- 模型选择是否需要区分 Provider 和 Model 两级；
- 可选模型列表由 Pi Runtime 动态提供，还是由 Forge 维护允许列表；
- 模型不可用、Provider 未配置或恢复时原模型缺失的处理方式；
- 哪些用户可以修改模型。

主要交互：

- 在模板 Agent 列表中查看模型；
- 使用受控选择器更换模型；
- 创建任务时查看本次任务将使用的模型；
- 明确标记“跟随模板”或“本次覆盖”；
- 修改前说明影响范围；
- 模型不可用时给出可操作的错误提示。

适合的可视化：

- Agent 卡片中的 Provider/Model 标签；
- 模板默认模型与本次实际模型的差异标记；
- 模型或 Provider 不可用状态。

## 9. Case 状态与用户动作

|---|---|---|

## 10. 重点可视化需求

### UI-VR-001 Case 状态与进度

采用模板驱动的阶段步骤视图，展示已完成、进行中、等待和阻塞状态。用户无需阅读日志即可判断当前阶段、当前步骤和下一步。

第一版不使用缺乏确定计算依据的百分比或预计完成时间。审核、返修等循环过程应展示轮次，而不是把重复执行伪装成线性百分比。

### UI-VR-002 Agent 泳道或协作时间线

在二级“执行记录”视图中展示 Agent、Turn、路由、返修和交付过程，并支持从生产概览中的相关状态或事件进入。

### UI-VR-003 产物版本链

展示版本父子关系以及有效、拒绝、替代和交付状态。

### UI-VR-004 版本 Diff

展示版本之间的内容变化，并支持用户选择比较版本。

### UI-VR-005 返修范围

展示 editable、frozen、changed 和 scope violation。

### UI-VR-006 Issue 生命周期

展示 Issue 从发现、返修、声称修复到验证关闭的过程。

### UI-VR-007 Issue、返修和版本关系

帮助用户理解一个问题由哪条指令处理、在哪个版本被修复。

### UI-VR-008 交付门禁

展示五项门禁检查及其阻断来源。

### UI-VR-009 异常与恢复时间线

展示暂停、失败、恢复和人工介入等重要控制事件。

### UI-VR-010 模板 Agent 关系

帮助用户理解模板中有哪些 Agent，以及它们如何协作。

## 11. 重点交互需求

### UI-IR-001 渐进式披露

默认展示业务结论，工程细节通过展开、抽屉或高级模式访问。

### UI-IR-002 状态驱动操作

页面只提供当前状态允许执行的操作，不展示无效或危险按钮。

### UI-IR-003 跨对象跳转

Issue、返修、版本、Turn 和门禁之间必须能够互相定位。

### UI-IR-004 明确反馈

创建、启动、停止、恢复和提交人工输入后，应明确显示操作是否被接受以及系统当前状态。

### UI-IR-005 危险操作确认

停止、重试、失效或其他可能影响已有生产结果的操作，需要说明影响范围并二次确认。

### UI-IR-006 空状态和异常状态

无任务、无产物、无 Issue、无门禁记录、读取失败等情况需要有明确解释和下一步入口。

### UI-IR-007 自动刷新

运行中任务需要自动更新。具体采用轮询、流式事件或其他方式在技术设计阶段决定。

### UI-IR-008 长内容阅读

故事、文案、提示信息和上下文可能很长，界面需要支持易读的长内容布局、定位和比较。

## 12. 产品体验原则

- 默认面向内容生产操作者，而不是数据库或 Agent 框架开发者；
- 先展示结论，再展示证据；
- 状态名称需要有用户可理解的中文表达，同时允许高级视图查看原始状态值；
- 所有关键状态必须来自 Forge 持久化数据；
- 生产任务启动后输入冻结，任何输入变更都通过创建新任务实现；
- 用户应当随时知道当前任务是否仍在运行；
- 阻塞状态必须同时说明原因和可执行的下一步；
- 产物、Issue、返修和门禁不能被拆成彼此孤立的信息区；
- 普通用户不能通过 UI 绕过状态机和门禁；
- UI 必须保持模板和业务无关；
- 高级诊断信息必须脱敏。

## 13. 当前能力基线

现有系统已经具备或部分具备：

- 模板列表和模板输入字段读取；
- 动态输入表单；
- Case 创建、运行和人工恢复；
- production、test、all 环境切换；
- Case 列表；
- Agent 泳道；
- Turn、消息路由和工具行为展示；
- 产物版本和行级 Diff；
- Issue 展示；
- 返修 editable/frozen 可视化；
- 交付门禁展示；
- waiting_human 提示和回答；
- 上下文快照和 provider 错误等诊断数据。

当前模型配置存在一个需要在产品化时修复的实现缺口：

- `scenario.yaml` 已为每个 Agent 声明 `model`；
- 当前 Real Pi 实际统一读取全局 `PI_MODEL_ID`；
- 当前 Provider 在 Adapter 中固定为 `deepseek`；
- CaseRunner 创建 Pi Session 时尚未传递 `agentConfig.model`；
- 因此模板声明的模型目前没有真正决定 Agent 的运行模型。

当前主要产品差距：

- 所有能力集中在单一页面，信息层级不清；
- 缺少以用户待办和当前结果为中心的工作台；
- 缺少独立的模板理解和选择体验；
- 创建任务交互较弱；
- Case 列表缺少搜索、筛选和清晰摘要；
- 用户需要阅读泳道才能判断整体进度；
- 产物、Issue、返修和门禁之间缺少直接关联；
- 异常和恢复仍偏工程提示；
- 原始工程信息与用户信息混在一起；
- 现有页面更适合回放验证，不适合作为完整生产操作台。

## 14. 与后续编排 UI 的关系

本文档当前首先细化单个 Forge Case 的 UI 产品化。

后续内置预定义编排器后，相关 UI 需求也继续写入本文档，但应建立独立章节，至少包括：

- 预定义流程列表；
- 创建流程运行；
- 流程阶段进度；
- 阶段与 Case 的关系；
- 上下游产物流转；
- 流程级异常和恢复；
- 下游失效传播；
- 最终流程交付。

当前单 Case UI 的任务、状态、产物、Issue、门禁和诊断概念，应尽可能能够被未来编排 UI 复用。

## 15. 阶段性成功信号

- 内容生产操作者无需 CLI 即可创建并运行一个 Forge Case；
- 用户进入任务详情后可以快速判断当前状态和下一步；
- 用户无需阅读 Agent 泳道、Turn 或工具日志即可判断任务状态、待办和当前结果；
- 用户可以找到当前有效产物和最终交付产物；
- 用户可以理解审核问题、返修范围和问题是否验证关闭；
- 门禁失败时，用户可以定位到具体阻断来源；
- waiting_human 可以在 UI 内完成闭环；
- 失败或恢复状态不会只显示不可理解的内部错误；
- 高级用户仍然能够获取脱敏后的完整运行证据；
- UI 不产生与数据库状态相冲突的第二套状态。
- 已启动任务不能被普通用户永久删除，归档后仍可恢复查看完整证据。
- 用户可以安全暂停和恢复运行中任务；停止后的任务不能原地继续。
- 异常任务是否可恢复由系统依据执行证据判定，用户不会面对危险的强制重试选项。
- 用户可以通过阶段和步骤状态理解真实进度，不会被虚假的百分比或预计时间误导。

## 16. 待持续细化的问题

- 工作台的具体信息架构；
- 第一版必须包含哪些页面；
- 标签由用户自由创建还是使用系统预设；
- 创建任务采用单页表单还是分步流程；
- 草稿采用自动保存、手动保存还是两者结合；
- 草稿离开页面时如何提示未保存内容；
- “基于此任务创建新任务”是否复制标签、模型覆盖和其他运行配置；
- 模板中心需要展示多少技术信息；
- Provider 与模型的可用列表由 Pi 还是 Forge 提供；
- 是否需要独立的模型 Provider 配置与连接状态页面；
- 草稿回收站是否支持恢复，以及保留多长时间；
- 归档任务默认如何搜索和筛选；
- 产物需要支持哪些复制、下载和导出格式；
- 长文本和故事正文的最佳阅读方式；
- Issue、返修和 Diff 的联合交互；
- 诊断模式的进入方式和权限边界；
- 实时更新采用何种体验；
- 桌面端、移动端和响应式范围；
- UI 视觉语言和组件体系；
- 后续编排 UI 的导航入口。

# Forge UI 技术需求文档

> 状态：技术需求拷问进行中
> 当前版本：0.29
> 首次建立：2026-07-29
> 对应产品需求：`docs/Forge_UI_需求文档.md`

## 1. 文档定位

本文档记录 Forge UI 产品需求冻结之后的技术需求、架构决策、约束、风险和待确认问题。

当前阶段只进行技术需求发现和方案收敛，不实施代码。全部技术分支确认后，再生成实施计划并进行只读对抗评审。

技术设计必须继续遵守：

- `contracts → domain → application → adapters → apps` 单向依赖；
- 通用平台不写死业务角色、阶段或产物类型；
- 模型不接触工程元数据；
- 交付由系统门禁决定；
- 产物和事件只追加、不覆盖；
- UI 不产生第二套生产状态；
- API Key、Token、Authorization Header 和模型隐藏思维链不得进入 UI、日志或业务数据；
- P0 必须通过真实 Pi、真实持久化和真实崩溃恢复验收。

## 2. 已确认架构方向

### TD-001 Next.js UI 与 BFF

保留现有 Next.js 应用，但重建其服务端边界：

- 浏览器只调用类型化 HTTP API；
- Next.js 服务端作为轻量 BFF，通过 application 层的查询服务和命令服务访问 Forge；
- Web 不再自行定义并执行 SQLite 业务查询；
- Web 不再通过拉起 CLI 子进程完成创建、运行或恢复；
- Worker 继续作为独立执行进程承担长时间 Agent 运行；
- 当前阶段不新增独立 Fastify 等 API 服务；
- 未来若出现远程部署、多用户或独立扩缩容需求，可以从 BFF 后拆出独立服务。

### TD-002 Electron 后续封装约束

Electron 是后续桌面交付形态，本轮先保证架构可封装，不立即建设 Electron 应用。

推荐封装方式：

- Electron 主进程启动随应用打包的 Next.js standalone 本地服务；
- Next 服务只绑定 loopback 地址和动态或受控本地端口；
- `BrowserWindow` 加载该本地地址；
- Electron 主进程统一管理 Next 服务、Forge Worker 和应用窗口的启动、健康检查、异常退出与关闭；
- 用户只需启动桌面应用，不需要手工执行 Web 或 Worker 启动命令；
- 不采用 Next.js 静态导出，因为 Forge UI 需要 BFF、SQLite、Worker 控制和其他 Node 服务端能力；
- Renderer 保持沙箱和上下文隔离，不开启 Node.js 集成；桌面原生能力只通过最小化 preload API 暴露；
- SQLite、Pi Session、日志和用户配置使用可配置的应用数据目录，不能依赖仓库工作目录；
- 打包时需要处理 `better-sqlite3` 等原生模块与 Electron ABI 的兼容和重建；
- Electron 退出前必须安全处理正在运行的 Worker，不能因窗口关闭而直接破坏生产证据。

该方向与 Next.js 官方 standalone 自托管能力、Electron 主进程和 Renderer 进程模型一致：

- [Next.js Self-Hosting](https://nextjs.org/docs/app/guides/self-hosting)
- [Next.js output 配置](https://nextjs.org/docs/15/app/api-reference/config/next-config-js/output)
- [Electron Process Model](https://www.electronjs.org/docs/latest/tutorial/process-model)
- [Electron Security](https://www.electronjs.org/docs/latest/tutorial/security)

### TD-003 Worker Supervisor 与 Case 进程隔离

采用“常驻 Supervisor + 持久化命令 + 每个 Case 独立 Worker 进程”的执行模型：

- BFF 只向 application 层提交运行、暂停、恢复和停止等命令，不直接创建 Worker 或 CLI 子进程；
- 命令在数据库中持久化，并具有稳定命令 ID、幂等键、状态、创建时间和处理结果；
- 常驻 Worker Supervisor 领取命令，并按照可配置的并发上限调度；
- 每个正在执行的 Case 使用独立 Worker 子进程，单个 Case 的 Provider、Pi Session 或未捕获异常不应直接击穿其他 Case；
- Worker 子进程必须继续使用现有执行租约、runner token 哈希和心跳机制确认执行所有权；
- Supervisor 只负责命令领取、进程生命周期和可观测性，不替代 Case 状态机，也不伪造业务状态；
- 子进程异常退出后，由持久化证据和 RecoveryService 判定 Case 是否可以恢复，不能由 Supervisor 直接标记成功或强制重跑；
- 同一命令被重复提交、Supervisor 重启或领取后崩溃时，必须依靠幂等与租约机制避免重复执行；
- Web 部署时 Supervisor 作为独立后台进程运行；Electron 封装后由 Electron 主进程启动和监控；
- 应用关闭、升级和系统关机时的排空、暂停、强制终止和恢复语义留待后续专项确认。

### TD-004 生产任务与 Case 分离

新增独立的 `production_tasks` 产品聚合，不把草稿、标签、归档等产品字段继续塞入 `cases`：

- `production_tasks` 保存用户可管理的信息，包括标题、模板修订身份、草稿输入、Agent 模型覆盖、运行环境、标签、来源任务、归档、回收站和草稿修订号；
- 草稿阶段允许修改；任务启动后，输入、模板修订、环境和模型配置冻结；
- 启动操作必须在一个受控事务中冻结任务配置、创建 Case 并建立任务—Case 绑定，任何一步失败都不能留下“显示已启动但没有可运行 Case”的半成品；
- 当前单模板任务绑定一个 Case；未来预定义流程任务可以通过绑定关系关联多个 Case；
- `cases` 继续保存不可随意修改的执行事实、运行身份和证据；
- `cases.created` 表示已经创建但尚未执行的 Case，不再兼任 UI 草稿；
- 运行中、等待、失败、停止和交付等任务状态从绑定的 Case 或未来流程运行投影得出，不在 `production_tasks` 中复制维护第二套运行状态；
- 归档和回收站属于任务可见性元数据，不改变 Case 状态和执行证据；
- 回收站只允许未启动草稿进入；已启动任务只能归档；
- “基于此任务创建新任务”复制已允许的配置形成新草稿，并通过来源关系关联；不复制 Case、产物、Issue、返修、门禁或执行 ID；
- 草稿修订号用于后续自动保存的乐观并发控制，具体冲突体验继续单独确认。

### TD-005 文件创作源与不可变模板注册库

采用“文件系统 Scenario Bundle 作为创作和导入来源，Forge 模板注册库保存不可变修订”的混合模型：

- 现有 `scenario.yaml + prompts + skills + validators` 继续作为可移植的模板创作格式；
- Forge 发现或导入 Bundle 时先执行完整校验，成功后注册不可变模板修订；
- 每个模板修订具有稳定修订 ID、场景 ID、场景版本、配置快照、完整 Bundle 哈希、来源信息、资源清单、父修订 ID、导入时间和校验结果；
- 模板资源按 Bundle 哈希内容寻址，导入后放入受 Forge 管理的不可变存储目录；Electron 环境使用应用数据目录；
- 草稿绑定明确模板修订 ID，不因源目录内容变化或新修订出现而静默升级；
- 启动时把模板修订 ID、配置快照和 Bundle 哈希冻结到生产任务与 Case 证据；
- 恢复时必须加载完全相同的不可变修订；修订资源缺失、哈希不一致或校验失败时 fail closed；
- UI 修改 Agent 默认模型时，基于原修订创建派生模板修订，并重新校验；不得覆盖原 YAML、原修订或已启动任务；
- 从外部文件重新导入相同 Bundle 哈希时复用已有修订，避免生成内容完全相同的重复版本；
- 被草稿、任务、Case、产物或门禁证据引用的模板修订不得删除；
- 模板注册库保存元数据和身份，具体资源采用文件内容寻址存储还是数据库 BLOB 留到存储设计时确认，但 Runtime 不得继续依赖可变源目录。

### TD-006 Pi 模型目录发现与 Forge 策略叠加

Provider 的注册、认证和模型事实目录归 Pi 管理；Forge 通过 Pi 的公开模型目录能力发现可用 Provider/Model，并叠加产品策略：

- 新 Provider、认证方式和凭据在 Pi 中添加，不在 Forge 中重复实现；
- Forge 通过受控 Adapter 调用 Pi `ModelRuntime` 的 `getProviders()`、`getModels()`、`getAvailable()` 和认证状态接口；
- “扫描 Pi 目录”指调用 Pi 的公开运行时 API，不读取或解析 Pi 的私有配置文件、缓存目录或内部数据库；
- Pi 返回 Provider、模型、能力和可用性事实；Forge 只维护允许列表、禁用规则、默认值、显示名称和顺序等产品策略；
- application 层的模型目录查询服务合并 Pi 事实与 Forge 策略，再向 BFF 返回脱敏 DTO；
- UI 可以查看 Provider/Model 和非敏感连接状态，并从允许且可用的模型中选择；
- Forge 不返回认证类型细节、凭据路径、API Key、Token 或 Header；
- 草稿保存每个 Agent 的 `provider_id + model_id` 以及“跟随模板”或“任务覆盖”来源；
- 启动时再次通过 Pi 校验模型存在且可用，然后把每个 Agent 的准确 Provider/Model 冻结到任务、Case 和 Session 证据；
- `RealPiAdapter` 必须按 Agent 接收准确 Provider/Model，不再固定 `deepseek` 或只读全局 `PI_MODEL_ID`；
- 恢复必须使用原 Provider/Model；原模型缺失或不可用时 fail closed，不允许静默替换；
- Provider/Model 目录的刷新、缓存和失效体验继续单独确认。

### TD-007 模型目录刷新与失效处理

Forge 对 Pi 模型目录采用“启动扫描 + 手动刷新 + TTL 后台刷新 + 最近成功快照”：

- BFF 或模型目录服务启动时异步扫描 Pi 公开目录接口，并设置明确超时；
- UI 提供显式刷新入口，新增 Provider 或模型后无需重启 Forge；
- 使用可配置 TTL 触发后台刷新，不监听或轮询 Pi 私有文件；
- 只持久化最近一次成功的非敏感目录快照、目录版本/哈希和刷新时间；
- 扫描失败时可以用最近成功快照支持查看和草稿编辑，但必须显示“目录可能已过期”和最近成功刷新时间；
- 没有成功快照时，模型选择器进入不可用状态并提供刷新与诊断入口；
- 任务启动前必须绕过缓存，通过 Pi 实时校验所有已选 Provider/Model；
- 实时校验失败时保持草稿，不创建 Case、不提交运行命令，并返回可操作错误；
- 已启动 Case 恢复时同样实时校验冻结模型；不可用时进入可解释的阻塞或恢复失败状态，不选择替代模型；
- 并发刷新需要合并，避免多个页面或请求同时触发重复网络刷新；
- 目录快照不包含 API Key、Token、Header、凭据路径或其他认证材料。

### TD-008 application Query/Command 与类型化 REST BFF

采用轻量 CQRS 边界，由 application 层向 Next.js BFF 提供明确的查询服务和命令服务：

- Query Service 返回面向 UI 的只读投影，包括任务列表、任务概览、执行记录、产物阅读、产物演进链、模板目录和模型目录；
- Command Service 承担保存草稿、启动、基于已有任务创建、归档、恢复草稿、暂停、恢复、停止、人工回答和刷新目录等用例；
- Query/Command 输入输出在 `contracts` 中使用 TypeBox 定义并进行运行时校验；
- BFF 使用明确的 REST Route 映射 application 用例，不引入 GraphQL、tRPC 或通用 CRUD；
- BFF 不直接暴露 `RepositoryPort`，不返回 SQLite 行、领域内部对象或任意字段更新能力；
- 普通短命令返回明确结果；需要 Supervisor 异步处理的长时间命令返回 HTTP `202`、稳定 `command_id` 和当前命令状态；
- API 错误使用稳定错误码、用户可理解信息和可选脱敏诊断引用，前端不得解析异常字符串判断行为；
- DB 路径、runner token、租约所有权、进程 PID、凭据和其他内部控制字段不得进入普通浏览器响应；
- Query Service 可以为了 UI 读取多个持久化对象并形成投影，但业务规则和状态判定必须复用 domain/application 能力，不能在 BFF 重写；
- application 服务不依赖 Next.js、HTTP、SQLite 或 Electron；BFF 只负责协议适配、身份无关的输入校验和响应映射；
- API 版本、分页游标、错误码表和具体 Route 结构在实施计划中固化。

### TD-009 SSE、持久化事件游标与轮询降级

实时更新采用单向 SSE，命令继续通过 REST 提交，不引入 WebSocket：

- application 在重要持久化变化的同一事务中追加轻量 UI 事件或事务性 outbox 记录；
- 事件只包含递增序号、事件类型、对象类型、对象 ID、发生时间和必要的版本引用，不复制产物正文、上下文或其他大型业务数据；
- Next.js BFF 提供 SSE 事件流，浏览器收到事件后按对象和版本失效或重新读取对应 Query 投影；
- 事件源必须来自持久化事件表，不能只使用进程内 `EventEmitter`，确保 BFF、Supervisor 和 Case Worker 跨进程一致；
- 浏览器断线重连时携带 `Last-Event-ID`，服务端从持久化游标之后继续发送；
- 游标早于事件保留窗口、事件出现缺口或服务端无法保证连续性时，发送 `resync_required`，客户端重新获取完整投影；
- SSE 连接失败或运行环境不支持时，降级为携带版本游标的轻量轮询，不再定时刷新整个页面；
- 事件至少覆盖任务、命令、Case、Turn、产物、Issue、返修、门禁、人工介入和模型目录变化；
- 当前页面位于最新位置时可以根据事件自动跟随；用户查看历史时只增加“有新进展”状态，不改变滚动或选中位置；
- SSE 事件不携带秘密或未脱敏诊断信息，客户端收到事件后仍需通过受控 Query 获取数据；
- 事件保留周期、清理方式、连接心跳和批量合并策略在实施计划中确定。

### TD-010 幂等键、乐观并发与数据库 CAS

所有写操作统一采用幂等请求协议，并根据对象类型使用修订号或预期状态进行并发保护：

- 每个用户意图生成稳定 `idempotency_key`，网络重试、页面重试和超时重试必须复用原键；
- 数据库对目标作用域、操作类型和幂等键建立唯一约束；
- 重复请求返回第一次请求的相同 `command_id`、当前状态或已完成结果，不重复产生副作用；
- 草稿写入携带 `expected_revision`，成功后原子递增修订号；
- 状态命令携带预期 Case 状态、控制版本或对应待处理行为 ID，并在事务中使用 CAS；
- 对象已经变化时返回 HTTP `409`、稳定冲突错误码和最新安全投影，前端不得自动覆盖；
- 启动任务在同一事务中完成草稿校验、配置冻结、Case 创建、任务—Case 绑定、运行命令追加和 UI 事件追加；
- 重复启动不能创建多个 Case；事务失败不能留下部分冻结或无绑定 Case；
- 人工回答绑定准确的 `request_human_input` 工具行为 ID，同一个请求只能成功回答一次；
- 暂停、恢复和停止必须同时验证目标状态、执行租约和已有控制命令，冲突时 fail closed；
- Supervisor 使用命令租约、心跳和 CAS 领取异步命令；领取者崩溃后允许安全重新领取，但不能重复执行业务副作用；
- 前端按钮禁用、loading 状态和防抖只用于改善体验，不能替代服务端幂等和并发校验；
- 幂等结果需要保留到相关任务和 Case 的数据保留周期结束，具体压缩策略在运维设计中确定。

### TD-011 权威事实按需生成 UI 投影

P0 的任务列表、概览和关联摘要从权威持久化数据按需计算，不新增不可重建的 UI 状态表：

- `TaskListQuery` 和 `TaskOverviewQuery` 从 `production_tasks`、任务—Case 绑定、Case、Turn、产物、Issue、返修、门禁和控制事件组装 UI DTO；
- 任务运行状态从绑定的 Case 或未来流程运行计算，不在任务表复制；
- 当前有效产物由统一的 domain/application 选择策略计算，BFF 和前端不得自行按“最新版本”猜测；
- 待办、阻断原因、可执行动作和下一步由 application 规则生成；
- 同一次投影读取使用一致的 SQLite 读事务或等价快照，避免各卡片读取到不同时间点；
- 投影返回 `source_event_seq`、对象修订号或 ETag，支持 Query 缓存、SSE 失效和冲突检测；
- 列表只加载必要摘要；执行记录、长正文、版本历史、Diff 和诊断证据分别分页或按需读取；
- 不在 `production_tasks` 中复制 `running`、当前产物 ID、Issue 数量、门禁结果等派生事实；
- P1 只有在性能测试证明按需计算无法满足目标时才增加物化投影；
- 物化投影必须可丢弃、可重建、带来源游标，不能参与状态机、门禁、恢复或执行决策；
- 投影重建失败只能影响读取体验，不能修改权威业务数据。

### TD-012 模板 presentation.progress 与证据驱动进度

扩展模板修订的可选 `presentation.progress` 展示元数据，由模板定义业务阶段和步骤，平台根据通用持久化证据计算状态：

- 每个阶段和步骤具有模板内稳定 `key`、用户可见 `label`、顺序和可选说明；
- 步骤通过通用 `evidence` 选择器引用 Agent Turn、产物版本、Issue、返修指令、人工输入、交付门禁或 Case 状态；
- 平台只实现通用证据类型和状态映射，不包含具体业务角色、阶段或产物名称的条件分支；
- 模板注册时校验 stage/step key 唯一，并校验引用的 Agent key、产物类型和其他模板内身份；
- 进度投影只产生待开始、进行中、等待、阻塞和完成等离散状态；
- 不计算缺乏真实依据的百分比、剩余时间或预计完成时间；
- 可重复步骤通过真实 Issue、返修指令或审核事件生成轮次节点，不能把循环过程伪装成线性完成；
- `presentation` 只影响查询投影和 UI，不得改变 Agent 路由、工具权限、Case 状态机、返修规则或交付门禁；
- 模板没有进度配置时，降级展示真实 Case 状态、当前 Agent/Turn 和事件时间线，不推断虚假步骤；
- 草稿升级模板修订时重新校验进度配置；已启动任务始终使用被冻结修订中的定义；
- 具体 evidence Schema、步骤状态归并优先级和轮次标识在实施计划中定义并以通用场景测试。

### TD-013 当前有效、最新创建与交付版本

建立统一 Artifact 版本选择策略，并修复当前发布候选版本时提前替换有效版本的实现冲突：

- `artifacts.current_valid_version_id` 只能为空，或指向同一 Artifact 下状态为 `approved` 或 `delivered` 的版本；
- 第一个版本尚未审核通过时，当前有效版本保持为空，Query 可以单独展示最新创建版本的带状态预览；
- 发布新的 `draft` 或 `under_review` 候选版本时，不更新 `current_valid_version_id`，也不立即把原有效 `approved` 版本标记为 `superseded`；
- 新候选版本审核通过时，在同一事务中把新版本设为 `approved`、把原有效 `approved` 版本设为 `superseded`、更新有效指针并追加事件；
- 新版本被拒绝、失效或发生返修越界时，当前有效版本和原有效版本状态保持不变；
- 交付成功时把当前有效 `approved` 版本原子迁移为 `delivered`，有效指针保持指向它；
- `delivered` 版本不可再迁移、覆盖或替换；同一 Artifact 最多只能存在一个 delivered 版本；
- Query 明确返回 `current_valid_version`、`latest_created_version` 和 `delivered_version`，不得用一个模糊的 latest 字段兼任三种语义；
- `latest_created_version` 按版本序号返回最新记录，无论其处于审核、拒绝、失效或替代状态，UI 必须显示准确状态；
- 读取有效指针时校验 Artifact 归属、Case 归属和版本状态；悬挂、跨 Artifact 或非法状态指针必须 fail closed 并产生诊断事件；
- Artifact 版本选择和批准切换规则放在 domain/application，BFF、CLI 和 Worker 共同复用。

### TD-014 草稿自动保存、恢复日志与冲突处理

草稿保存采用服务端乐观并发，并使用浏览器本地恢复日志防止网络或窗口异常造成输入丢失：

- 每次自动保存提交完整草稿快照、`expected_revision` 和稳定幂等键；
- 输入停止后防抖保存；切换创建步骤、显式保存退出和启动任务前立即 flush；
- 服务端成功保存后返回新修订号、保存时间和草稿内容哈希；
- 网络失败或服务端暂时不可用时保留当前页面内容，并把未保存快照写入 IndexedDB 恢复日志；
- 服务端确认保存后清除对应或更旧的本地恢复日志；
- 再次打开草稿时，如果本地日志比服务端修订更新，只提示用户可以恢复，不自动覆盖服务端；
- 多标签页、多个窗口或其他客户端已经修改草稿时，服务端返回 `409` 和最新修订；
- 冲突发生后停止该草稿的自动保存，防止持续产生冲突请求；
- 冲突界面只提供重新加载服务端版本，或使用本地内容创建一个来源明确的新草稿；
- 不执行自动字段合并，也不提供绕过修订号的强制覆盖；
- “保存草稿并退出”必须等待服务端保存成功，失败时留在当前页面；
- “创建并运行”前必须确认全部修改已经持久化、修订号仍为最新、本地没有待发送写入；
- 本地恢复日志按任务 ID 隔离，设置清理机制，不包含 Provider 凭据、Token 或其他秘密；
- 如果未来支持远程、多用户或共享设备，需要重新评估 IndexedDB 中业务内容的本地保留策略。

### TD-015 写入前脱敏与查询前防御性脱敏

诊断数据采用两道脱敏防线，禁止把“前端不显示”误当作秘密保护：

- 所有 Provider Error、工具参数、工具结果、上下文快照和结构化日志在持久化前通过统一 `SecretSanitizer`；
- 优先依据工具 Schema、字段分类和明确白名单决定允许保存的结构；
- 对 Provider 等外部返回的未知文本再执行敏感字段名、凭据格式和 Header 模式检测；
- 检测到的秘密在写入前替换为 `[REDACTED:<TYPE>]` 等明确占位符，不保存可逆原文；
- 脱敏器解析失败、超时或遇到不支持结构时，丢弃诊断正文并保存 `redaction_failed` 元数据，不能回退写入原文；
- Diagnostic Query 对历史数据再次执行防御性脱敏，避免旧数据或导入数据绕过新规则；
- 普通用户 Query 不返回完整上下文、工具参数、工具结果或原始 Provider Error；
- 复制、下载和导出诊断信息使用相同或更严格的 Query 脱敏规则；
- Pi 的 reasoning、hidden chain-of-thought 或内部推理通道不采集、不持久化、不返回；
- Provider 认证只对 UI 返回已配置、未配置、可用或异常等非敏感状态；
- 结构化日志不得记录用户输入正文、产物正文、完整环境变量、绝对 DB 路径、Token、Cookie 或 Authorization Header；
- 业务内容可以按产品要求保存为输入、消息、上下文和产物，但不得被误归类为秘密凭据；遥测与普通日志默认不复制业务正文；
- 使用合成 API Key、Token、Header、Cookie 和连接字符串进行泄漏测试，扫描数据库、日志、API、SSE、诊断复制和 UI 输出；
- 具体数据分类、字段标注、占位符格式和历史数据修复方案在实施计划中固化。

### TD-016 SQLite 显式前向迁移与升级保护

用显式、可审计的 Schema Migration 体系替代 Repository 构造函数中的零散列检测：

- 增加 `schema_migrations(version, name, checksum, applied_at)`；
- 每个迁移使用仓库内固定版本文件，包含唯一版本、名称、内容 checksum 和明确的升级步骤；
- 迁移默认只向前执行，不提供生产数据库自动降级；
- 每个迁移在 SQLite 事务中执行，成功后才写入迁移记录；
- 应用启动时校验已应用迁移的 checksum，历史迁移文件被修改时拒绝继续；
- 迁移前 Supervisor 停止领取新命令，并等待 Case Worker 正常结束或进入已确认的安全暂停边界；
- 迁移前 checkpoint WAL、关闭 BFF/Supervisor/Worker 的旧数据库连接，并获取独占迁移锁；
- 使用 SQLite Backup API 为每个待迁移数据库创建可恢复备份，并记录来源版本、目标版本和校验信息；
- production 与 test 数据库分别迁移、分别备份、分别记录 Schema 版本；
- 迁移失败时终止应用启动，保留原数据库与备份，不创建空库、不跳过版本、不继续写入；
- 应用声明支持的最低和最高 Schema 版本；旧应用遇到更高版本数据库时拒绝写入；
- 数据回填必须幂等，不重写产物正文、Issue 事件、返修历史、门禁结果和其他追加式证据；
- Electron 更新后首次启动先完成迁移，再启动 BFF 和 Supervisor；
- 测试覆盖空库、当前旧库 fixture、重复迁移、checksum 不一致、中途异常回滚、WAL、并发进程和 Electron 首次启动场景；
- 备份保留数量、磁盘不足处理和用户恢复入口在 Electron/运维设计中继续确认。

### TD-017 本地并发与持久化调度

P0 采用保守的单机调度默认值，同时把并发能力设计为可配置策略，而不是写死的平台限制：

- 默认最多同时运行 `1` 个 Case，超出上限的启动或恢复命令进入持久化队列；
- “排队中”是 application 根据待处理命令、命令租约和 Case 执行证据生成的任务投影，不新增虚假的 Case 运行状态；
- 最大并发数可配置，修改后只影响后续调度，不强行终止或抢占已经运行的 Case；
- P1 在高级设置中提供并发配置入口；默认用户不需要理解或调整该参数；
- 除全局 Case 并发上限外，允许为 Provider 或 Model 配置更严格的并发上限、速率预算和退避策略；
- Provider/Model 限制来自 Pi 暴露的能力事实与 Forge 策略，不读取 Pi 私有配置，也不把凭据写入调度记录；
- 命令优先级依次为：运行控制命令、人工介入或崩溃恢复命令、新任务启动命令；
- 同一优先级默认按进入队列时间 FIFO 调度，并使用等待时长提升等防饥饿机制，避免低优先级任务永久无法运行；
- 每个运行中的 Case 仍使用独立 Worker 子进程；并发配置只改变 Supervisor 的领取与启动数量，不削弱 Case 隔离；
- Worker 持有数据库写事务的时间必须尽可能短，禁止在模型调用、外部工具调用或等待人工输入期间占用写事务；
- SQLite 使用 WAL 和明确的 busy timeout，并对热点写入、锁等待和队列领取冲突进行可观测记录；
- Provider 限流或暂时不可用时，按照持久化重试时间和有界退避重新调度，不由进程内定时器独占状态；
- Supervisor 重启后从命令、租约、Case 状态和持久化证据重建可运行队列，不依赖仅存在于内存中的排队顺序；
- 调度器不得因为命令重领、进程重启或配置变化而重复执行已经产生业务副作用的步骤；
- P0 默认并发为 `1` 是安全运行基线，不是平台能力上限；提高并发前必须通过真实 Pi、SQLite 锁竞争和多 Worker 崩溃测试。

### TD-018 安全边界暂停、恢复与终态停止

P0 采用协作式控制，把暂停边界收敛为一个完整 Pi Turn 结束之后，不承诺 Turn 内即时打断：

- 在 Case 领域状态中增加明确的 `paused`，并保存暂停前的可恢复状态或等价检查点信息；
- 暂停、恢复和停止都通过持久化、幂等的控制命令表达，不由 BFF 或 Supervisor 直接改写 Case 状态；
- Worker 在每个完整 Pi Turn 结束并完成相关持久化事务后检查控制请求；
- 收到暂停请求但尚未到达安全边界时，Query 投影显示“正在等待安全暂停”，不提前把 Case 标记为 `paused`；
- 到达安全边界后，Worker 原子追加暂停证据、保存检查点、释放执行租约并正常退出；
- 恢复命令校验 Case 确实处于 `paused`，并使用原来冻结的模板修订、Provider/Model、Pi Session 和检查点启动新的 Worker；
- 恢复不得偷偷升级模板、切换模型、重建空 Session 或重放已经提交成功的 Turn；
- 停止是不可恢复的终态操作；Worker 优先在同一安全边界协作停止，持久化 `stopped` 证据后退出；
- Supervisor 对长时间没有到达安全边界或失去响应的 Worker，按可配置超时依次尝试进程间协作信号、优雅终止和强制终止；
- 暂停请求发生强制终止时不得标记为 `paused`，而应在确认进程退出和租约失效后进入 `waiting_recovery`；
- 停止请求发生强制终止时，先由恢复协调器核对最后持久化 Turn、工具行为和外部副作用证据，再将 Case 收敛到 `stopped`；
- 无法确认结果的在途工具或外部副作用必须留下“结果未知”的诊断证据，并禁止自动重试；
- 控制命令、Case 状态迁移、租约释放和 UI 事件使用 CAS 与事务边界，避免暂停、恢复和停止互相穿透；
- Electron 或 Supervisor 关闭不能把普通进程退出伪装成用户停止；未完成安全暂停的 Case 必须按崩溃恢复规则处理；
- P0 不实现 Turn 内抢占、Provider 请求取消、运行中模型切换或资源预占；这些能力只有在 Pi 提供可靠取消协议且真实验收通过后才进入 P1。

### TD-019 Fake、UI 与真实 Pi 三层发布门禁

P0 建立三层测试与发布验收体系；Fake Pi 只承担可重复的基础验证，不能替代真实运行证据：

- 第一层在每次提交和 CI 中运行领域规则、状态机、Contract、application 用例、SQLite 集成、命令幂等、租约和恢复测试；
- 第一层使用 Fake Pi 与故障注入保证快速、确定、可重复，并覆盖成功、拒绝、超时、重复命令和并发冲突；
- 第二层使用浏览器 E2E 覆盖内容生产操作者的 P0 主路径，包括创建草稿、选择模型、启动、实时更新、断线重连、暂停、恢复、停止和结果查看；
- UI E2E 必须通过正式 BFF、application Query/Command、持久化命令和 Supervisor 链路，不能用页面内假数据替代；
- 第三层作为发布候选硬门禁，至少使用一个真实 Pi Provider/Model 完成真实运行与进程级崩溃恢复；
- 真实 Pi 验收使用运行时发现并冻结的准确 Provider/Model，不依赖测试脚本中写死的默认模型；
- 真实 Pi 测试断言工具行为、持久化证据、状态迁移和不变量，不断言模型生成的具体自然语言；
- 真实验收必须证明恢复的是原 Case、原 Pi Session、原模板修订和原 Provider/Model；
- 验收必须证明已提交 Turn、产物版本、Issue、返修指令、门禁结果和工具副作用没有被重复创建；
- BFF、Supervisor 或 Worker 重启后，SSE 游标和 Query 投影必须重新同步到权威持久化事实；
- 每次发布候选生成脱敏验收报告，记录代码提交、Schema 版本、模板修订、Pi 版本、Provider/Model ID、故障注入点、断言结果和时间；
- 验收报告不得包含 API Key、Token、Header、隐藏思维链、完整业务正文或未脱敏 Provider Error；
- 真实凭据只通过运行环境提供，不写入测试 fixture、日志、数据库业务表或报告；
- 真实 Pi 或进程级恢复门禁未通过时，P0 状态必须如实标记为未完成，不能用 Fake Pi 结果代替；
- 现有 `crash-recovery-e2e.cjs` 和 `crash-recovery-realpi-e2e.cjs` 作为历史基线保留参考，但新版门禁必须覆盖 Supervisor、持久化命令、暂停控制和 UI 投影链路。

### TD-020 Supervisor 重启与存活 Worker 接管

Supervisor 崩溃或重启时，仍然健康的 Case Worker 继续运行；Supervisor 不是 Worker 正确执行的单点依赖：

- Worker 自己持有并续约 Case 执行租约、写入心跳和完成命令结果，不依赖 Supervisor 代写业务状态；
- Worker 在 Supervisor 暂时离线时仍检查持久化控制命令，因此暂停或停止意图不会只存在于进程间内存消息；
- 每次 Worker 启动生成稳定到该进程生命周期的 `worker_instance_id`，并将其与 Case、命令和执行租约绑定；
- PID 只作为诊断信息，不能单独证明 Worker 身份，也不能作为强杀或接管依据；
- 新 Supervisor 启动后从命令、租约和心跳重建运行视图，并优先通过受限本地 IPC 使用 `worker_instance_id + case_id + lease generation` 完成身份握手；
- 握手成功且租约仍有效时，新 Supervisor 接管健康监控，不启动第二个 Worker，也不要求原 Worker重跑当前 Turn；
- 暂时无法完成 IPC 握手但心跳与租约仍有效时，保持观察并阻止重复调度，不凭 PID 强杀未知进程；
- 心跳停止后仍需等待租约过期，并确认原 Worker 不再拥有合法写入权，才能领取恢复命令；
- Worker 的每次业务写入继续验证租约 generation 与 runner token，旧 Worker 即使迟到恢复也不能越过已转移的所有权；
- 新 Supervisor 不得通过扫描系统中所有 Node.js 进程猜测所属关系，也不得终止无法证明由 Forge 启动的进程；
- Supervisor 重启期间 Worker 正常完成时，由 Worker 原子提交 Case/命令完成证据；新 Supervisor 重建时识别该结果，不重复执行；
- IPC 地址、实例身份和控制令牌只保存于受限运行目录或持久化哈希字段，不进入普通 Query、SSE、日志或 UI；
- 验收必须包含 Supervisor 被强杀、Worker 继续完成，以及 Supervisor 重启后重新接管仍在运行 Worker 两种场景。

### TD-021 分阶段 Turn Journal 与工具副作用约束

用可恢复的分阶段 Turn Journal 替代当前跨越 Pi 调用和工具执行的 SQLite 长写事务：

- Turn 使用明确、可校验的阶段记录，例如 `prepared`、`model_running`、`response_recorded`、`actions_applying`、`completed`、`failed` 和 `outcome_unknown`；
- 开始 Turn 时用短事务追加 Turn 身份、Agent、序号、输入消息引用、上下文快照引用、请求哈希、Pi Session 引用和执行租约 generation；
- 提交 `model_running` 后在数据库事务外调用 Pi，模型网络等待期间不持有 SQLite 写锁；
- Pi 返回后用短事务保存模型响应引用、finish reason 和结构化工具调用清单，再进入工具执行阶段；
- 每个工具调用具有稳定 `tool_action_id`、参数哈希、目标作用域、状态和幂等键；
- Forge 内部工具的领域副作用、工具行为完成记录和相关 UI 事件在同一个短事务中原子提交；
- 已经处于 `completed` 的工具行为再次执行时返回原结果引用，不重复创建产物、Issue、返修、门禁结果或其他副作用；
- 所有工具行为完成后，用短事务完成 Turn、写入输出消息引用并提交路由或 Case 状态迁移；
- 恢复器根据 Journal 阶段决定后续动作：尚未调用、核对模型结果、继续未完成工具行为或只补齐 Turn 最终提交；
- 已保存模型响应时不得再次调用 Pi；已完成工具行为不得再次执行领域副作用；
- 崩溃发生在 Pi 已处理但响应尚未可靠持久化的窗口时，优先通过冻结的 Pi Session 和响应身份核对结果；
- Pi 无法提供可靠结果核对时，把 Turn 标记为 `outcome_unknown` 并让 Case 进入 `waiting_recovery`，不盲目重新调用模型；
- `failed` 表示已有确定失败结果；`outcome_unknown` 表示结果无法确认，两者不能混用；
- P0 工具只允许两类副作用：能够与 Forge 权威数据在同一事务提交，或提供稳定幂等键与结果核对协议；
- 外部非事务工具必须声明副作用类别、幂等能力、核对方式和未知结果处置策略；
- 无法幂等、无法核对结果的外部副作用工具不进入 P0 模板能力；
- 模型调用本身可能产生无法撤销的 Provider 费用；Forge 保证不重复提交业务副作用，但在 Provider 不支持幂等调用时不能虚假承诺费用层面的 exactly-once；
- Turn Journal、工具行为和状态迁移全部采用追加式证据、CAS 与执行租约校验，禁止恢复过程覆盖历史记录；
- 现有 `TurnExecutor` 跨 `await` 保持事务的实现属于待替换基线，不能作为新版并发和恢复架构继续保留。

### TD-022 进程级故障注入窗口矩阵

P0 用确定性检查点和真实进程终止覆盖命令、Worker 与 Turn Journal 的关键崩溃窗口：

- Fake Pi 进程级测试覆盖以下全部窗口：
  1. 命令已经持久化但尚未被 Supervisor 领取；
  2. 命令已经领取并取得命令租约，但 Worker 尚未成功启动；
  3. Worker 已取得 Case 租约、Turn 已进入 `prepared`，但尚未调用 Pi；
  4. Pi 调用正在进行且模型结果尚未持久化；
  5. 模型响应和工具调用清单已经持久化，但工具行为尚未执行；
  6. 一个或多个工具副作用已经提交，但 Turn 尚未完成；
  7. Turn 已经完成，但运行命令尚未标记完成或 UI 事件尚未被消费。
- 真实 Pi 发布门禁至少覆盖：Pi 调用进行中强杀 Worker、Turn 完成后但命令完成前强杀 Worker、Worker 运行时强杀并重启 Supervisor；
- 测试检查点只通过测试模式下的进程间握手暴露，不提供生产 HTTP 调试接口，也不依赖不稳定的固定等待时间；
- 测试驱动器等待目标检查点确认后，真正终止对应 Worker 或 Supervisor 进程，而不是仅在同一进程中抛出模拟异常；
- 每个场景使用隔离但真实的 SQLite 数据库、Pi Session 目录、模板修订和应用数据目录；
- 进程终止后重新启动正式 Supervisor/Worker 链路，并使用原数据库和原运行目录恢复；
- 每个窗口都必须验证：恢复原 Case、使用原 Session/模板/模型、租约安全转移、命令最终收敛、Case 状态合法；
- 每个窗口都必须验证：无重复 Turn、消息、产物版本、Issue、返修、门禁结果、工具行为和 UI 事件；
- 模型结果无法核对的窗口必须收敛到 `outcome_unknown` 与 `waiting_recovery`，不能为了让测试继续而伪造成功或自动重跑；
- 已完成但尚未被 UI 消费的事件允许重新投递，消费者依靠事件序号和对象修订去重；
- UI E2E 在恢复完成后验证 SSE 重连、全量重同步、任务状态、Agent 过程和产物侧栏与 Query 投影一致；
- 故障测试同时扫描数据库、日志、命令结果、SSE 和报告，验证不存在凭据与隐藏思维链泄漏；
- 所有窗口先以 Fake Pi 稳定通过；真实 Pi 的最小三项随后作为独立发布门禁运行，不能反向用真实模型的不确定性掩盖确定性故障。

### TD-023 本地 Web 先行与 Electron 封装边界

当前阶段先把本地 Web 产品和真实运行链路做完整，Electron 只保留清晰封装入口，不进入本轮 P0 实施范围：

- P0 交付形态是运行在本机的 Next.js Web、BFF、Supervisor、Case Worker 和 SQLite；
- Web 主路径、状态管理、恢复、真实 Pi 和崩溃门禁全部通过后，才启动 Electron 封装工作；
- 当前不创建 Electron 主进程、preload、安装器、签名、自动更新或桌面原生菜单；
- 当前验收不得因为“以后会放进 Electron”而跳过本地 Web 的启动、关闭、错误处理和数据目录设计；
- Next.js 保持可生成 standalone 服务的构建边界，不能依赖仓库源码目录或开发服务器才能运行；
- BFF、Supervisor 和 Worker 提供明确、可由外部宿主管理的启动、健康检查、安全关闭与退出码协议；
- application 和 domain 不依赖 Electron、BrowserWindow、IPC、安装目录或 Windows API；
- 浏览器端只使用标准 Web 能力；未来需要文件选择、系统通知等桌面能力时，通过可替换 capability 边界接入；
- 数据库、Pi Session、模板资源、日志、备份和用户配置都从显式应用数据根目录派生，不写入只读安装目录；
- 本地服务只监听 loopback；未来 Electron 通过受控本地地址加载同一 Web 应用，不维护第二套 UI 或业务 API；
- 当前 Web BFF 的 HTTP/SSE Contract 在 Electron 中继续复用，Renderer 不直接访问 SQLite、文件系统或 Worker；
- 进程发现和终止封装为跨平台 Adapter，业务层不得出现 `taskkill`、PID 扫描或其他 Windows 专属分支；
- Electron 首个内部 Alpha 暂定为 Windows 11 x64、按用户安装；内部版本可暂不签名，对外分发前必须完成代码签名门禁；
- macOS、Linux 和 Windows ARM 不在首个 Electron Alpha 支持范围，但平台无关层不得主动阻断后续适配；
- Electron 的安装器、签名、自动更新和主进程生命周期在本地 Web 冻结后另开需求与技术拷问，不提前纳入当前完成声明。

### TD-024 `forge ui` 统一启动与安全关闭

本地 Web 提供一个面向操作者的统一入口 `forge ui`，避免要求用户分别启动多个服务：

- `forge ui` 是本地运行控制器，不承载领域规则，也不直接代替 Supervisor 或 Case Worker；
- 启动时先解析配置和应用数据目录，执行目录权限、磁盘空间、Schema 兼容性和依赖完整性预检；
- 每个应用数据目录只允许一个活动的 UI/BFF/Supervisor 实例，使用带所有者身份和心跳的单实例锁；
- 单实例锁不能只保存 PID；发现陈旧锁时必须验证进程身份和租约后才能回收；
- 启动顺序为：获取实例锁、执行必要迁移、启动 Supervisor、启动 Next.js standalone BFF、等待健康检查、打开默认浏览器；
- BFF 默认只绑定 `127.0.0.1`，选择可用本地端口后把实际地址写入受限运行时状态；
- 健康检查分别报告数据库、Schema、Supervisor、命令队列、Pi 目录和 BFF 状态，但不返回凭据或内部令牌；
- 重复执行 `forge ui` 时，如果已有健康实例使用相同数据目录，则只打开其页面，不再启动第二套进程；
- 如果已有实例不健康，启动器输出脱敏诊断和恢复建议，不直接抢锁、强杀或创建新数据库；
- 启动中任一步失败时，停止本次新启动且尚未交接的组件、释放可安全释放的锁，并保留原数据库与诊断证据；
- 浏览器窗口关闭不停止 BFF、Supervisor 或正在运行的 Case；
- 第一次 `Ctrl+C` 或正常关闭请求进入 draining：停止领取新启动命令，并为运行中 Case 提交安全暂停请求；
- 启动器等待 Worker 到达已确认的 Turn 间安全边界；达到边界后依次关闭 BFF、Supervisor 并释放实例锁；
- 超过等待时间时明确显示仍在运行或等待恢复的 Case，不把它们伪装成已暂停，也不自动标记为停止；
- 强制关闭启动器后的存活 Worker、失效租约和未完成命令继续遵守 Supervisor 重启与崩溃恢复规则；
- 开发模式保留独立的 `npm run dev` 等入口，但必须使用隔离的开发数据目录，不能与操作者实例同时写同一数据库；
- `forge ui` 的进程编排通过应用层之外的宿主 Adapter 实现，为未来 Electron 主进程复用相同生命周期协议留出入口。

### TD-025 应用数据根目录与环境隔离

本地 Web 的持久化数据从一个显式应用数据根目录派生，不能继续默认散落在仓库工作目录：

- Windows production 默认数据根目录为 `%LOCALAPPDATA%\ForgeAI`；
- `forge ui --data-dir <path>` 可以显式覆盖数据根目录；
- `FORGE_DATA_DIR` 可以提供环境级覆盖，解析优先级为命令行参数、环境变量、平台默认值；
- 启动时把目标目录解析为规范化绝对路径，并验证可创建、可写、可加锁和磁盘可用；
- production、development 和 test 必须使用完全隔离的数据根目录，禁止仅靠不同数据库文件名共享 Session、锁或备份目录；
- 标准目录至少包括：
  - `db/`：production/test 环境内的 SQLite 数据库和 WAL；
  - `sessions/`：Forge 管理的 Pi Session 持久化引用与运行数据；
  - `templates/`：不可变模板修订和内容寻址资源；
  - `logs/`：经过脱敏和轮转的结构化日志；
  - `backups/`：数据库迁移与用户触发的可恢复备份；
  - `runtime/`：实例锁、本地 IPC、端口和进程身份等短生命周期状态；
  - `cache/`：可删除、可重建的目录快照或查询缓存。
- `runtime/` 与 `cache/` 不得成为恢复、门禁或业务事实的唯一来源；
- 仓库中的 `data/` 只用于开发、测试和显式 fixture，不作为操作者 production 默认目录；
- 数据目录在进程运行期间不可切换；参数或配置变化必须在安全关闭后重启整套本地服务；
- 显式选择一个空目录时执行正常首次初始化；选择已有目录时必须先校验实例身份、Schema 和目录结构，不静默创建第二个空数据库掩盖错误；
- Forge 不复制、迁移或备份 Pi 的 Provider 凭据；凭据仍由 Pi 的公开认证与配置能力管理；
- 普通 UI 不返回数据根目录的完整绝对路径；高级诊断可在本机明确操作下展示经过最小披露的路径信息；
- 未来 Electron 继续把同一个数据根目录传给 BFF、Supervisor 和 Worker，不创建第二套数据库或隐式迁移到不兼容结构；
- 非 Windows 平台的默认路径由平台 Adapter 决定，application/domain 只接收已经解析的数据根目录。

### TD-026 备份、日志与低磁盘空间门禁

P0 使用保守、可配置的默认空间策略，只自动清理可重建或明确过期的数据：

- 脱敏结构化日志默认最多保留 14 天，且所有轮转日志总量不超过 100 MB；
- 超过日志期限或总量上限时按最旧文件优先清理，当前活动日志通过原子轮转切换；
- `cache/`、确认过期的 `runtime/` 状态和没有权威引用的失败临时文件可以自动清理；
- 自动清理前验证规范化路径位于当前应用数据根目录的指定可清理子目录内，禁止对计算错误或越界路径执行递归删除；
- 每个数据库默认保留最近 3 个经过校验的迁移备份；
- 创建并验证新备份后才允许淘汰更旧备份，且任何时候不得删除唯一一个已知可恢复备份；
- 用户主动导出或明确标记保留的备份不参与自动清理；
- Schema 迁移前至少要求 `2 × 当前数据库文件大小 + 512 MB` 的可用空间，并计入待导入资源的额外估算；
- 可用空间低于 1 GB 时，UI 显示持续但不阻断阅读的低空间警告；
- 可用空间低于 512 MB 时，禁止启动新任务、导入模板和执行迁移，并向运行中 Case 提交安全暂停请求；
- 低空间门禁不能直接把运行中 Case 标记为暂停；Worker 未到达安全边界时仍显示真实状态；
- SQLite 返回磁盘已满或写入失败时立即停止继续产生副作用，保留错误证据，并在仍可安全写入时把 Case 收敛到可恢复阻塞状态；
- 自动清理永不删除 SQLite 数据库、WAL 中未 checkpoint 的数据、Pi Session、模板修订、产物、Issue、返修、门禁结果或其他生产证据；
- 高级设置提供分类占用、最近备份、日志范围和安全清理入口，不提供任意路径删除器；
- 容量阈值、日志上限和备份数量允许在高级配置中调整，但调整不能绕过迁移所需空间计算和“唯一可恢复备份不可删除”规则；
- 磁盘门禁与清理行为必须包含边界值、并发写入、路径穿越、清理中崩溃和备份校验失败测试。

### TD-027 文件 CAS 与模板修订元数据

模板采用“文件内容寻址存储（CAS）+ SQLite 元数据”，不把完整 Bundle 作为数据库 BLOB 保存：

- SQLite 保存模板修订、场景身份、父修订、来源、Bundle 哈希、资源清单、每个资源的 SHA-256、大小、媒体类型和引用关系；
- 实际 `scenario.yaml`、Prompt、Skill、Validator 和其他允许资源保存到 `templates/objects/<sha256>`；
- 对象路径只由经过格式校验的内容哈希生成，不拼接来源文件名、场景名或用户输入路径；
- 导入时先复制到应用数据目录内的独立 staging 目录，逐项计算哈希并执行 Bundle 与资源校验；
- 导入拒绝绝对路径、`..` 路径穿越、逃出根目录的符号链接、设备文件、大小写折叠冲突和超出限制的文件或 Bundle；
- Windows 路径校验同时处理保留设备名、替代数据流和规范化后重名；
- 单文件大小、总 Bundle 大小、文件数量和允许资源类型使用可配置上限，超限时在注册修订前失败；
- 全部对象写入临时文件、完成 fsync/关闭并校验哈希后，再用同文件系统原子移动进入对象目录；
- 相同 SHA-256 的资源复用已有对象；复用前重新验证对象大小和哈希，检测到损坏时 fail closed；
- 只有全部资源对象已经可靠落盘且清单校验成功后，才能在数据库事务中创建模板修订和引用记录；
- 数据库提交失败时，已落盘但未被引用的对象视为可回收孤立对象，不得反向伪造模板修订；
- Runtime 只通过被冻结的模板修订清单解析资源，加载时校验对象存在、哈希和大小，不继续读取可变来源目录；
- 草稿、任务、Case、产物或门禁证据引用的模板修订及其对象不可删除；
- 孤立对象清理只处理经过宽限期、重新扫描仍没有权威引用且不在 staging 中的对象；
- SQLite Backup 只备份元数据和引用；完整灾备或用户导出必须同时包含数据库与所引用 CAS 对象，并生成可验证清单；
- 不使用大型 SQLite BLOB 保存模板资源，避免常规查询、WAL、迁移备份和数据库锁被资源体积放大；
- CAS Adapter 位于基础设施边界，domain/application 只依赖模板修订、资源引用和内容哈希 Contract。

### TD-028 P0 不建设鉴权与权限体系

当前产品是本机单操作者工具，P0 不把精力投入用户与权限基础设施：

- 不建设账号、登录、用户会话、角色、权限矩阵、功能授权或高级功能权限门禁；
- 所有已实现功能默认对当前本机操作者可用，高级功能只通过信息层级降低干扰；
- 不增加自定义 CSRF Token、本地身份令牌或一套额外的请求来源认证协议；
- 不为未来可能的多用户、局域网或远程部署提前建设权限抽象；
- 本地 Web 继续遵守已经确认的 `127.0.0.1` 监听范围，不提供 `0.0.0.0` 或局域网暴露配置；
- BFF 仍执行 Contract 校验、业务前置条件、幂等、CAS、租约和状态机规则，这些属于正确性保护，不是权限管理；
- 浏览器与 BFF 维持同源部署，不为跨域客户端开放 CORS；
- 如果未来明确进入局域网、远程、多用户或共享设备场景，再单独开展鉴权、安全边界和权限需求拷问；
- 当前技术问题优先聚焦 UI、BFF、Supervisor、Worker、Pi、持久化、恢复和真实验收链路。

### TD-029 前端服务端状态与表单状态边界

前端采用最小、职责明确的状态组合，不在浏览器中复制 Forge 运行状态机：

- TanStack Query 管理任务列表、任务概览、Case、命令、Agent 过程、产物、Issue、返修、模板和模型目录等服务端状态；
- Query Key 使用稳定对象身份、筛选条件、分页游标和投影版本组成，禁止用显示文案作为缓存身份；
- SSE 事件只携带对象身份和版本，并触发精确 Query 失效、重新获取或增量游标推进；
- 前端不根据 SSE 事件自行推演 Case 状态、当前有效产物、门禁结论或下一步动作；
- SSE 断线、游标过期或收到 `resync_required` 时，以 Query 全量投影重新建立权威视图；
- React Hook Form 管理创建任务向导、模板参数、Agent 模型覆盖和高级设置等表单状态；
- TypeBox Contract 同时用于表单输入的运行时校验和 REST DTO 校验，服务端仍是最终规则判定者；
- 草稿自动保存把表单快照提交给 Command API，并继续使用 IndexedDB 恢复日志与 `expected_revision` 冲突协议；
- 当前任务、选中的 Agent/Turn/产物版本、侧栏开关和筛选条件使用 URL 状态或组件局部状态；
- 需要跨少量相邻组件共享的纯展示状态可以使用小范围 React Context，不建立全局业务 Store；
- P0 不引入 Redux、Zustand 或其他全局客户端状态框架；
- 不使用 Next.js Server Actions 承担写操作；所有写入继续通过类型化 REST Command、幂等键和 CAS；
- Next.js Server Component 可以用于静态壳层和首屏读取，但持续更新的生产界面由 Query + SSE 管理；
- Mutation 成功只根据服务端返回结果更新最小缓存或触发失效，不乐观伪造运行状态和产物；
- 前端状态测试覆盖 SSE 重连、事件乱序、重复事件、Query 失效、分页、草稿冲突和页面刷新恢复。

### TD-030 版本化本地配置与热更新边界

进程级非敏感配置保存在应用数据根目录下的版本化 `config.json`：

- 配置包含明确的 `schema_version` 和配置修订号；
- 配置只保存并发上限、命令与关闭超时、模型目录刷新周期、日志轮转、备份保留和磁盘阈值等非敏感设置；
- TypeBox Contract 定义配置 Schema，并在启动、读取和写入时执行同一套严格运行时校验；
- 未知字段、缺失必填字段、非法枚举和越界数值均返回稳定错误码与具体字段路径，不静默忽略；
- 配置不存在时从代码内受版本控制的安全默认值创建首版；配置损坏时停止正常启动，不自动替换为空配置；
- 写入使用临时文件、flush、原子替换，并保留最近一次通过校验的配置备份；
- UI 通过 application Command 修改配置，提交 `expected_revision` 与幂等键，不直接写文件；
- 并发上限、模型目录刷新周期、日志轮转和备份保留等允许热更新，但只影响后续调度或下一次维护周期；
- 应用数据目录、监听地址、数据库位置、Runtime 路径和其他启动级配置修改后必须完整重启；
- Query 明确返回每项配置的当前值、来源、是否可热更新、是否需要重启和最近生效时间；
- 已经启动的任务继续使用创建时冻结的模板、模型和运行配置，不受全局配置热更新影响；
- 命令行参数与环境变量只覆盖数据目录、端口、日志级别等启动级参数，优先级遵守已经确认的启动解析规则；
- API Key、Token、Provider Header、Pi 凭据路径和其他秘密不得进入 `config.json`、配置备份或配置 Query；
- 配置变更追加审计事件，但不复制完整业务内容或秘密；
- `forge config validate` 或等价预检能力在不启动 Worker 的情况下报告配置问题；
- 开发与测试环境使用各自数据根目录内的独立配置，禁止测试热更新 production 实例。

## 3. 当前代码基线

- `apps/web` 使用 Next.js 14 App Router；
- 页面服务端组件通过 `apps/web/lib/db.ts` 直接读取 SQLite；
- 创建、运行、恢复 API Route 当前通过 CLI 子进程完成操作；
- Web 内重复定义了部分数据库记录类型和查询；
- `apps/worker` 当前是一次执行一个新 Case 或恢复一个 Case 的进程入口，不是常驻任务调度器；
- `RealPiAdapter` 当前统一使用 `deepseek` Provider 和全局 `PI_MODEL_ID`；
- `CaseRunner` 创建和恢复 Pi Session 时尚未把每个 Agent 的模型作为真实运行参数传入；
- SQLite 已持久化 Case、租约、Session、Turn、消息、路由、产物版本、Issue、返修、上下文、门禁、工具行为和控制事件。
